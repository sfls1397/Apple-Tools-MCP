# Code notes

Why the code is the way it is, kept here because the code carries no comments (`docs/TYPES-AND-LINT.md`, the comment ban). Each section names the file it belongs to. Narration, history and dividers were deleted; only reasons that are not visible in the code or its tests live here.

## npm bin wrappers (`bin/apple-tools-mcp.js`, `bin/apple-tools-indexer.js`, `bin/apple-tools-http.js`)

- npm 12 pack and publish rewrites a `bin` target named `index.js` and drops it with the warning `script name index.js was invalid and removed`, so each CLI has its own wrapper. The guard is `tests/unit/npm-bin.test.js`.
- `bin/apple-tools-indexer.js` injects `--mode=indexer` and `bin/apple-tools-http.js` injects `--transport=http`, so a realpath to the wrapper still starts that daemon or server. `permissions` (and `http-token` for the HTTP wrapper) still win over the injected flag, the same contract as the `apple-tools-indexer` bin name.
- `bin/apple-tools-mcp.js` is the MCP stdio server and the `permissions` subcommand.

## `scripts/postinstall.js`

Print-only reminder after an install or upgrade. It must never run GUI or TCC probes unattended: a LaunchAgent or a headless npm cannot click Allow. The operator runs `apple-tools-mcp permissions` on the host's UI. The guard is `tests/unit/permissions.test.js` ("is a package-bin subcommand, not an unattended postinstall probe").

## `scripts/audit-index.js`

Usage: `node scripts/audit-index.js [--sources emails,messages] [--max-items 50]`; `--sources calendar --max-items 0` audits a single source with no item cap. The report goes to standard output.

## `scripts/smoke-mail-read.js`

- Read only: every `mail_search` hit must be readable by `mail_read`. For each hit it checks what `mail_read` needs: the `File` path passes `validateEmailPath`, the file exists and its headers parse.
- A hit whose file is gone means the index holds stale paths (for example after a move to a new Mac). The indexer re-paths those on its next pass.
- Writes nothing, sends nothing, needs no indexer lock. Usage: `node scripts/smoke-mail-read.js [--limit=30] ["receipt" "meeting"]`. Exit 0 when every hit is readable, 1 when any is not, 2 when there were no hits.

## `scripts/smoke-writes.js` (the write ship gate)

- It covers the Automation and privacy classes that gate this package's writes: Mail compose (Automation to Mail.app), Messages account and service lookup (Automation to Messages.app), Contacts CRUD (AddressBook class, through Contacts.app) and Calendar CRUD (calendars class, through Calendar.app).
- `mail_send` with `dry_run` never talks to Mail, so the Mail step runs a real `make new outgoing message` and discards it. A hang or timeout there is TCC or Automation denied, not "Mail.app missing". Nothing is sent. Mail and Messages are separate Apple Events targets: a Contacts or Calendar grant does not include them.
- Mail, Messages, Contacts and Calendar must all pass on the Node host; that is the ship gate. A missing grant for any one of the four fails `--apply`. Contacts and Calendar CRUD are expected to fail under a host app that holds neither entitlement: a documented host limitation, not a package failure.
- The write path launches Contacts.app before CRUD, so keep Contacts, Mail and Messages running on the host. Calendar does not need to stay open (EventKit).
- The default is a dry run: no contact or event is created, edited or deleted. It is not a no-op: it reads contacts from the AddressBook database and calls `calendar_list_calendars`, a live Calendar.app query and a real TCC touch that can prompt or be denied. A dry run treats that listing as advisory (`calendarListSeverity(false)` is a warning), so a denial does not fail a run that changed nothing. Only `--apply` treats it as an error. The Mail compose step is advisory on a dry run in the same way (a refused prompt is WARN).
- `--apply` performs real create, edit and delete round trips; `--keep` leaves the test items; `--calendar=Work` picks the calendar. Test items are clearly named and removed unless `--keep`. No credentials, tokens or personal data are involved.
- Ship-gate precondition: the smoke test must exercise the same path production MCP clients use, so a real run needs the write bridge (writes execute inside the launchd-started daemon, where node is the responsible process) or an explicit `--allow-local` acknowledgement that this process itself is the responsible one, which is only true when a parent like Terminal.app or launchd started it. Running in process under a foreign parent (an embedded agent shell, for example) produces an AppleScript denial that says nothing about whether the package works.
- Every write goes through `dispatchWriteTool`, the production dispatcher, not the write modules directly. Importing them directly is what made the smoke test bypass the bridge and fail the Mini ship gate (guard: `tests/unit/write-tools.test.js`, "dispatches through the production write path, not the write modules directly").
- The read side runs first: it proves Full Disk Access independently of the write path. Mail runs first among the writes so the first-run Allow prompt covers Mail in the same pass as Contacts and Calendar.
- The Mail compose-and-discard and Messages lookup helpers exist only in this script; they are not MCP write tools. With the write bridge up, `--apply` also runs the public `mail_draft`, so the launchd-owned node is fail-closed for Mail (same verb, nothing is sent).
- Calendar choice: prefer an On My Mac calendar, so a Calendar.app delete is reliable if the EventKit remove still misses. EventKit add and remove is the primary path on iCloud (`writeOnly` can delete events it created). An explicit `--calendar=` wins.
- Smoke events are placed well in the future so they never collide with anything real on the calendar.
- The script's main block runs only when invoked directly, so the helpers stay unit-testable.

## `contacts.js`

- Contacts reads go straight at the AddressBook sqlite file, so they depend on Full Disk Access for the process macOS holds responsible. They do not depend on the AddressBook entitlement that gates Contacts.app and CNContactStore writes. Reporting the difference keeps a plain Full Disk Access problem from being mistaken for the host entitlement gap.
- iCloud-synced contacts live in the `Sources` subdirectory of the AddressBook folder; the main database is the fallback, and a source with no rows is skipped.
- `ZUNIQUEID` is the Contacts.app person id the write tools address contacts by. A schema without it must still load contacts for search.
- Memory bounds: at most 50,000 contacts, 10 emails and 10 phones per contact, so a very large contacts database cannot exhaust memory. The lookup maps are cached for 5 minutes.
- Phone numbers are normalized to digits, keeping a leading `+` for international numbers; a US number is reduced to 10 digits by dropping the leading 1, and the `+` is kept only when no leading 1 was dropped.
- Name lookup tries an exact full name first, then first name, nickname and partial matches; `lookupContact` tries email (the most specific), then phone, then name.

## Gate scripts (`.githooks`, `.security`, `.cursor`)

- Both history scans (`.security/metadata.py`, `.githooks/pre-push`, the gate and `merge-pr.py`) read only the history being checked, never `--all` and never `rev-list --all`: the head the gate checks, or each tip a push sends. The worktree shares the repository's refs, so `--all` took in other jobs' branches and scratch worktrees and failed pushes and gates on someone else's scratch commit. A delete pushes no commits, so neither scan runs for it; the file scan still does. Guards: `.security/test_standard.py`: `test_history_ignores_another_jobs_scratch_worktree`, `test_pre_push_checks_only_the_pushed_commits` and `test_gate_and_merge_scan_only_the_checked_head`.
- After a push, GitHub's PR head can lag the branch by a few seconds, so `local-gate.py` waits up to `HEAD_WAIT` seconds before refusing when the origin branch already holds the local commit (ported from the Toolbox). A closed PR never waits; an unpushed commit or an unreadable origin refuses at once. Guard: `test_pr_head_lag_after_a_push_is_waited_out`.
- Only the owner's newest `local-gate` status on the exact SHA counts for a merge; GitHub Actions are not the gate. The merge sends the SHA as a condition, so GitHub rejects a changed PR head atomically.
- Public tool attribution in pre-existing history is not a personal identity, but new commits must always use GitHub noreply, including tool-generated commits. `cat-file` reads the real commit headers because a mailmap cannot hide an identity.
- `.security/scan.py`: Semgrep 1.180.0 misparses a valid TypeScript regex as an HTML comment, so its spelling is rewritten in the disposable scan copy only, with the same pattern and flags; runtime and index bytes are never modified. Advisory chains are pinned for every affected installed version, not just the name. Staged scans use explicit staged targets so an unstaged worktree or unrelated files are never scanned; tools, configuration, package metadata and candidate source come from the index. Tests and scripts are scanned; only generated and vendor paths are ignored. Tool errors, source snippets, private paths and config are never echoed.
- `.security/test_gates.py` probes never make test commits, so they never bypass a real repository's hook. Staged metadata would trigger a real npm, so only source is checked, with a fake npm that returns an empty successful audit.
- `.security/languages.py` selects an SDK compatible with the installed compiler for the Clang analysis, then fails on findings.
- `.cursor/install-gitleaks.sh` and `install-semgrep.sh` serve Cursor Cloud on Linux: they install only the checksum-verified pinned release, Semgrep needs Python 3.10 or newer, default cloud images omit `ensurepip` (so the same pin comes from the system pip), and exports last for that script only (the always-applied rule sets `PATH` in new shells). CI has no committer identity by default, so `.cursor/install-security.sh` sets one and never inherits a runner hostname. Default-image cloud agents skip `environment.json`, so tools install to `~/.local/bin`.

## `index.js`

- Entry modes: `--mode=indexer` (also the `apple-tools-indexer` bin) is the canonical indexer daemon; `apple-tools-mcp permissions` is a short-lived CLI with no MCP and no indexer; `--transport=http` (also `apple-tools-http`) serves the same tools as stdio but every request must carry a bearer token (`lib/httpAuth.js`); `apple-tools-mcp http-token` is a short-lived CLI that prints the token.
- The token goes to standard output only, so `$(apple-tools-mcp http-token)` is scriptable. Any one-time generation banner goes to standard error from `loadOrCreateHttpAuthToken()` itself.
- HTTP exposes every tool stdio exposes, including the write tools. What changes is reachability (LAN or Tailscale instead of only this process's parent), so a bearer token is required; stdio has no such check because a locally spawned child is already trusted by whoever spawned it.
- HTTP creates a fresh `Server` and transport pair per request instead of reusing the module-level `server`. The SDK's `StreamableHTTPServerTransport` in stateless mode (`sessionIdGenerator: undefined`) is single use: the Protocol class throws "Already connected to a transport" on a second `connect()` before the first closes, which a shared instance would hit under any concurrent access. This matches the SDK's own stateless example.
- `ownsIndexLock` is true only while this process won the indexer lock. It is distinct from `sessionIndexComplete`: a secondary instance that lost the lock never completes a local cycle and must not stay on "still indexing" forever. Index-backed tools wait only while this process owns the lock and has not finished its cycle; lost-lock secondaries fall through to `isIndexReady()`, and `initDB` re-lists the shared on-disk tables and must not cache an empty first connect.
- A worker orphaned by an abrupt parent death with its event loop blocked still holds `indexer.lock`, and launchd never kills it (`lib/orphanWorker.js`).
- The write bridge is daemon only: it serves writes for stdio clients whose host app cannot be granted Contacts or Calendar automation (`lib/writeBridge.js`). It starts before any index work, because launchd started the daemon so node owns the TCC prompts, and writes must stay available even if the vector index is missing, locked or unreadable. A failed readiness probe must not take the daemon (or its write bridge) down; it assumes a first run and lets the cycle report the details. A startup indexing failure is logged rather than rejected, because an unhandled rejection would tear down the daemon and the write bridge with it.
- Writes never wait on the vector index: they talk to Mail, Messages, Calendar and Contacts directly and must keep working while the indexer daemon holds the lock.
- stdio clients exit when the host closes stdin, but the indexer daemon, the HTTP server and the short-lived CLIs must not: LaunchAgent and KeepAlive often attach stdin to `/dev/null`, and the CLIs exit on their own. A caller that pipes a batch and closes stdin still gets every reply, because in-flight requests finish (up to `STDIN_CLOSE_DRAIN_MS`) before exit (guard: `tests/unit/stdio-drain-on-close.test.js`).
- MCP stdio, when the indexer daemon (or another instance) holds the lock, skips the background refresh and uses the shared index. When nothing holds the lock it indexes locally, using the same heartbeat path as the daemon so a long first-index cycle cannot look like a stale lock to another waiter. The HTTP server never takes the lock (it could hold it while the indexer daemon restarts); rebuilds run from stdio or the indexer.
- While `indexAll()` is running, the progress monitor allows searches but does not clear `indexingInProgress` or release the lock, because overlapping writes can corrupt LanceDB. A cycle ends by unblocking searches on failure as well as success, so tools are never stuck forever; the indexer daemon keeps `indexer.lock` for the process lifetime, and the MCP local fallback releases it between cycles. No progress for 10 minutes (checked every minute) is treated as a hung cycle.
- Tools that answer from the shared vector index add a note to their replies when the index has not finished a pass in several intervals, worded by whether the `indexer.lock` holder is alive (still refreshing, stuck or down).
- `rebuild_index` acquires the lock to prevent parallel rebuilds across MCP instances, starts the rebuild in the background and returns immediately without awaiting it.
- `startIndexing()` kept as a no-op for external callers; indexing runs on the background timer, once at startup and then every `INDEX_INTERVAL`.
- Smart search routes by detected intent (calendar, messages, mail indicators; all sources when none match), searches the sources in parallel and groups multi-source results into one-hour time buckets, newest first. Person search resolves the contact first, searches mail by up to 3 email addresses (last 365 days) and messages by up to 3 phone numbers, and falls back to a name search when no contact is found.
- Email bodies are read only from the Mail directory (path traversal check), and HTML is stripped with a safe method that avoids ReDoS.

## `indexer.js`

**Configuration and storage**
- `APPLE_TOOLS_INDEX_DAYS_BACK` is an optional date filter for email indexing only. The default is unlimited (all emails); `30` caps the window (tests do this); `0` explicitly disables filtering. Messages and calendar are always indexed in full: the cap applies where mail files are found by modification time, not to email header dates (an old-dated message can be modified recently), and calendar events have no file modification time, so a date filter would lose historical context.
- `BATCH_SIZE` is 64 for embedding throughput; no delay between batches is needed because benchmarks showed no thermal throttling. Mac Absolute Time counts from Jan 1 2001 00:00:00 UTC (978307200 seconds after the Unix epoch).
- One LanceDB connection per process. A first connect that saw an empty catalog must not be cached, because MCP stdio has to pick up tables the indexer daemon already wrote. The connection uses a capped Session so LanceDB's caches do not grow to their 6 GB and 1 GB defaults in the long-lived daemon.
- Indexed ID sets stay in memory between passes and are re-read only when the table version moves. Email files skipped as Message-ID duplicates are remembered so the same IMAP copies are not parsed every pass (copies that left the lookback window are forgotten). After compaction (new table versions) the IDs are re-read once on the next pass. Reading the IDs retries with exponential backoff (at most 5 seconds) and then throws instead of returning an empty set, because an empty set makes the pass add duplicate entries.
- `@huggingface/transformers` is imported lazily: it loads `sharp` at import time, and a static import crashes Linux (and any host without the platform's native `sharp`) before the `search.js` formatters and pronoun helpers can load.
- Embedding: one forward pass for a batch, with a 30 second timeout per batch so a stuck embedding cannot hang the process; on a batch timeout (other errors are rethrown) it falls back to one text at a time with a 10 second timeout each, and a text that still fails gets a zero vector. The model's dimension is 384 (all-MiniLM-L6-v2); the result is a flat `Float32Array` of batch size times 384.

**Email**
- Mailboxes have a deduplication priority (lower number first): primary mailboxes, then organizational folders, then catch-all folders, then folders users rarely search; unknown or custom folders get 50 (between Archive and All Mail). When the same email exists in several folders (IMAP behavior), the copy from the higher-priority folder is indexed so mailbox searches work, so files are sorted by priority before indexing, which keeps INBOX copies over Junk and Trash copies. Duplicates are found by Message-ID, including two copies of one new email in the same batch and across batches.
- The full scan (first run and `rebuild_index`) includes `.emlx` and `.partial.emlx` (not fully downloaded over IMAP; `*.emlx` also matches `*.partial.emlx`). A partial email may lack complete headers but is still indexed. Permission and IO errors propagate, so `indexEmails` never persists a timestamp for an empty scan and skips real mail forever. The scan is async so the daemon keeps answering `writer.sock` during a slow scan.
- The incremental scan uses `find -mtime`, not `mdfind`, because Spotlight can have stale or incomplete indexes. The last timestamp is saved from before the pass starts, so mail arriving during indexing is picked up next time, with a 1 day buffer for files modified during the previous scan; the first run falls back to the full scan.
- Apple Mail envelope files start with a byte count line that is skipped before the RFC822 content; folded headers are unfolded so long From, Subject and To values are complete; HTML is stripped with the safe method to avoid ReDoS.
- Stale rows (guard: `tests/unit/indexer-stale-email-rows.test.js`): rows whose file is gone happen when Mail rebuilt or renamed its mailbox folders (a move to a new Mac), a `.partial.emlx` finished downloading, or a message moved. Without the pass those rows keep dead paths forever (`mail_read` fails on every hit) and the live copies are skipped as Message-ID duplicates of the dead rows. A stale row whose Message-ID matches an unindexed live file is re-pathed to it (the copy from the highest-priority mailbox, as a fresh index would pick) and keeps its embedding; the rest are removed. Quiet passes only stat the cached paths. "Gone" means ENOENT or ENOTDIR only: a file that exists but cannot be read right now (EACCES on one mailbox) is not stale. An unreadable Mail folder (lost Full Disk Access, a scan error) is never treated as "every email is gone", because that would empty the index. When the pass finds work, the full scan is used for indexing so relocated mail older than the lookback is not missed; a `DAYS_BACK` cap keeps its own window. A new path is added before the old one is deleted, so a failed delete leaves a stale row that the next pass removes and a failed add loses nothing; a duplicated old path must not become a duplicated new path.
- SQL string literals for LanceDB (DataFusion) escape only the single quote; a backslash is literal there, so doubling it (as `escapeSQL` does) would make a path containing one never match.

**Messages**
- `attributedBody` (NSKeyedArchiver BLOB) holds the message text when `text` is NULL (newer macOS). Four strategies are tried in order, and the first valid result wins: the NSString plus `+` pattern (backward compatibility), a direct UTF-8 scan for the longest printable run of at least 20 characters, an NSKeyedArchiver `$objects` parse for modern macOS, and regex patterns for common message structures. The text must be mostly printable characters. Messages with no text after extraction are filtered out, and the hex blob is dropped from memory.
- The query returns chat info, group chat detection and attachments. `sinceTimestamp` is Unix ms and is converted to Mac Absolute Time nanoseconds. Booleans are cast explicitly to avoid LanceDB schema inference issues.

**Calendar** (guard: `tests/unit/calendar-today.test.js`)
- Reading must throw on a source-read failure: a silent empty list would look like "every event was deleted" and the stale-entry pass would wipe the calendar index. Events are keyed by `dbId` alone (no timestamp in the ID, which created duplicates), and the same format is used when reading back. Stale entries are deleted in chunks of 100 with OR conditions (LanceDB compatible) after validating the IDs.
- The occurrence window is 10 years back and 10 years ahead. The indexer's query reads `OccurrenceCache` for recurring and non-recurring events, grouped to avoid duplicate rows for recurring events; the date-bounded query behind `calendar_date`, `calendar_upcoming` and `calendar_recurring` returns one row per occurrence and must not `GROUP BY ci.ROWID`, which would collapse a multi-occurrence event.
- `OccurrenceCache.day` is each occurrence's local midnight, so `calendar_upcoming` and `calendar_recurring` bound by today's local midnight, never now: comparing `day` to now dropped all of today (all-day and later-today events) after midnight (fixed in 3.3.5). The bounds are converted from unix ms to Apple/Core Data seconds (unix minus 978307200). A calendar copy with no `OccurrenceCache` rows at all is not a readable calendar, so it says so instead of reporting an empty day. The first local day of a multi-day event is the occurrence-end local date minus (days minus 1), as day math, which is DST safe.
- `includeUid` adds the iCal UID that the calendar write tools address events by; older Calendar schemas may lack the column, so callers retry without it, and `calendar_date` must still return events from a schema without `unique_identifier`.
- Calendar.app holds a lock on the live database, so one query reads a snapshot copy of `Calendar.sqlitedb` (plus wal and shm) in a temporary folder and deletes it afterwards. The index-cycle variant awaits the sqlite3 reads so the daemon's event loop (and `writer.sock`) stays free.

**Passes and rebuilds**
- Rebuild drops the requested tables, then resets the connection cache so `initDB()` re-opens or recreates them instead of holding stale or empty handles, then re-indexes with a forced full scan. A source whose read was skipped (lost Full Disk Access, no store) indexed nothing after its table was cleared, so that is not a clean rebuild and does not count toward a full pass. A clean full rebuild is a finished pass over all three sources, like `indexAll`; a partial one leaves the other sources as old as they were.
- Readers of the shared index (the HTTP server, lost-lock stdio clients) use the recorded times to say when the index has stopped refreshing: the last full pass (a `rebuild_index` pass over emails, messages and calendar with no error; `indexAll` records its pass time when at least one source was read without error), and the last regular pass that could read no source at all, which is never a success time and is cleared by a finished pass.
- Compaction and old-version cleanup run daily, and only after a pass that wrote something: every `add()` leaves a small data file and a new version, and without compaction the tables grow thousands of fragments that every full read opens.
- Guards: `tests/unit/indexer-email-pass.test.js` and `tests/unit/rebuild-pass-time.test.js`. Per-batch duplicate checks run twice on purpose (within the batch, then against the index) so duplicates never reach a table; the Message-ID set is updated after each batch so later batches see earlier batches' IDs.

**Direct queries and tools**
- LanceDB `where` clauses with quoted column names are unreliable, so recent-item queries fetch all rows and filter, sort and limit in JavaScript, with a fallback that selects minimal columns for older indexes. Message threads sort oldest first for conversation view. A sender or chat handle matches a contact through the name's resolved handles, and from-me rows match through the 1:1 chat's handle.
- Limits are validated to prevent SQL issues, and one extra row is fetched to detect whether more exist. `mail_senders` excludes junk and trash mailboxes by default.
- `getUnreadCount` (in `indexer.js`, the unread email count) validates the mailbox name to prevent AppleScript injection and escapes it for a double-quoted AppleScript string as well (belt and suspenders). `calendar_week` starts from Monday (a Sunday goes back 6 days) and ends Sunday. `mail_thread` matches by subject because Message-ID is not indexed; it validates the file path against traversal and verifies the file exists before reading.

## `search.js`

- Caches: the embedding cache and the result cache each expire after 5 minutes (`EMBEDDING_CACHE_TTL`, `RESULT_CACHE_TTL`) and evict the oldest entry when at capacity. Follow-up context (recent queries and entities, used to resolve "they", "them", "their") expires after 5 minutes (`CONTEXT_EXPIRY_MS`).
- Pronoun resolution never uses `RegExp#test` with a `/g` regex: `lastIndex` is stateful and can skip the first (or only) pronoun on this or a later call. A fresh regex plus `replace()` is `lastIndex` safe; do not hoist the regex or call `test()` on it (guard: `tests/unit/search-logic.test.js`).
- Entity extraction limits input length and name length (1 to 20 letters) and uses simple patterns so a hostile query cannot cause ReDoS. Dates come from chrono-node; a "last N days" pattern is handled separately; extracted filters apply only where the caller did not set an explicit option (explicit options take precedence).
- Query expansion returns the original query plus a simplified one (time modifiers removed) and at most one synonym variant, deduplicated, at most 3 variants. Negation accepts `NOT term`, `-term` and `without term`, and drops results containing a negated term.
- Results from the variants are merged with Reciprocal Rank Fusion, `RRF(d) = sum of 1/(k + rank(d))` with k = 60, keeping the document with the better original score. Confidence: a top score below `MIN_CONFIDENCE_SCORE` (0.5) is low confidence, and so is fewer than 3 results with a top score below 0.7. Hybrid scoring is `(1 - vector distance) * 0.7 + keyword score * 0.3` (`VECTOR_WEIGHT`, `KEYWORD_WEIGHT`): an exact word match scores higher than a partial match (0.5), and stop words are removed first.
- The self-correcting search embeds all variants in parallel using cached embeddings and searches them in parallel; it retries with a broadened query (time constraints and narrowing prepositions removed) only when there are no results at all, not on low confidence, which would cost unnecessary embedding calls.
- The vector connection is shared with `indexer.js`, so a first empty catalog is refreshed the same way `isIndexReady()` is, not a second handle that can stay empty. Tables are pre-warmed to remove first-query latency.
- Dates: a day's end is the next local midnight, not plus 24 hours, which is wrong on DST transition days (the same for the calendar's date range). Direct `Date` parsing is the fallback after chrono-node; AppleScript dates such as "Friday, January 10, 2025 at 9:00:00 AM" are handled explicitly.
- Email: junk and trash mailboxes are excluded by default unless the caller asked for them or named a mailbox. Results sort by relevance or date, and the count before slicing drives the "more results" indicator. The sender email is resolved to a contact name.
- Unread filtering asks Mail.app through AppleScript for unread subjects and senders across all mailboxes (not just the inbox), and more emails are fetched when filtering for unread because unread ones may not be the most recent. An email matches only when both subject and sender match: that prevents false positives when several emails have similar subjects. The index stores the sender in two formats (display name only, or display name plus `<email>`) and AppleScript returns `name <email>`, so only the display name is compared, strictly, and the part before "via Cloaked" counts when the full names differ. Subjects match exactly, or when one is a prefix of the other (the index truncates subjects), or when the first 40 characters match (calendar invites with different times). An AppleScript failure is reported, and an AppleScript success with no unread mail is a real empty result.
- Messages: a from-me message shows who it was sent to (contact name and handle, or the group chat); a conversation is shown oldest first.
- Calendar: results sort ascending. Live date queries read `Calendar.sqlitedb`, not the vector index. The local day runs from local midnight to the next local midnight. A timed event is clamped to the day and counted in minutes from local midnight, so an overnight event (23:00 to 01:00) contributes only the slice that falls on that day. Free time skips all-day events (reminders and holidays, not time blocks), merges busy periods and reports free slots including the time after the last event.
- Calendar rows carry the iCal UID as `eventId`: the id the calendar write tools address events by. The rank-fusion dedup helper `deduplicateResults` is the legacy single-query dedup; the multi-variant path uses RRF.
- Meeting-link passcodes ride in URL query strings and "Passcode:" lines, so titles, locations and notes print URLs without queries and with passcode values hidden.
- A calendar tool result that failed to read the calendar becomes a thrown error, so the MCP dispatcher answers `isError: true`; a failed read must never look like an empty day. Formatters accept both the new `{events, showing, hasMore}` shape and the old array. The internal functions are exported for tests.

## `lib/appleScript.js`

- Scripts are always built from escaped literals (never string-concatenated shell) and run through `safeOsascript` (`spawnSync`, `shell: false`). `asString`, `asInteger` (validated, throws rather than interpolating unchecked input) and `asBoolean` emit the literals.
- macOS TCC attributes an Apple event to the responsible process, which for a stdio MCP server is the app that launched node, not node itself. A host app without the Contacts or Calendars entitlements therefore makes the child's Apple events fail no matter what permissions node has. `lib/writeRouting.js` uses the classification to hand the work to the launchd-started indexer daemon, where node is the responsible process.
- Sentinels raised by the scripts let callers map them to clean errors instead of raw AppleScript text. Denial signatures: Apple event errors -1743 and -10004, or "not permitted" and "not authorized" text. App-missing signatures include -1728 and "can't get application"; when the bundle is on disk that is attribution, not a missing app. Contacts (and sometimes Mail) report -600 when the app is installed but not launched: a cold start, not an Automation deny (cold `tell application "Contacts"` under launchd often returns -600 instead of auto-launching).
- `osascript` itself missing (not macOS, or a stripped `PATH`) is never an attribution problem, because nothing ran. A bare "spawnSync osascript" is deliberately not matched: a TCC-denied Mail compose hangs until `spawnSync` times out (`spawnSync osascript ETIMEDOUT`), and that string also contains it and must not be reported as "Mail.app could not be reached". On the Mini, `tell Mail to get name` returns but `make new outgoing message` blocks until timeout when node to Mail Automation is denied: that hang is a TCC deny, not a missing app.
- ETIMEDOUT or -1712 is a hang, not a TCC deny. Mail maps that kind to `MAIL_SEND_TIMEOUT_GUIDANCE` (find, reply, open, send), never `MAIL_TCC_GUIDANCE`, and `calendar_remove` must never print Calendar-denied copy for ETIMEDOUT alone: add and edit succeed (Automation granted) and then the delete hits `spawnSync` ETIMEDOUT or -1712, which is an iCloud or CalDAV hang or a confirmation dialog, not -1743 or -10004. Callers must not rewrite it as `CALENDAR_TCC_GUIDANCE`; `isHardTccDenial` is the real deny test. Deleting a detached event specifier often returns "Can't get event ... (-1728)", a missing object, not a missing app, checked before the generic -1728 path. Installed and not running (-600) is a cold launch, not Automation. With the app on disk, "can't get application" means macOS refused to let the responsible process drive it: an Automation or attribution problem.
- `needsHostTccAdvice` decides whether `dispatchWriteTool` appends the MacBook or Mini host recovery text. Handlers rewrite raw Apple events as the contacts, calendar, messages or mail TCC guidance or `ATTRIBUTION_GUIDANCE`, which do not contain the -1743 or -10004 signatures `isTccDenial` looks for (except `MAIL_TCC_GUIDANCE`); `MAIL_SEND_TIMEOUT_GUIDANCE` must never match.
- `extractAppleEventCodes` and `formatOsascriptDiagnostic` pull known AppleEvent and spawn codes out of `osascript` stderr, so smoke can print them instead of guessing TCC; always include the diagnostic on a `calendar_remove` failure so a Mini `--apply` stops looking like a TCC deny.
- Guidance copy: it names the host constraint without claiming the package can grant another app's entitlements. Contacts writes are the sharpest case: reads query the AddressBook sqlite file directly and only need Full Disk Access on the responsible process, while writes go through Contacts.app and CNContactStore, gated by the AddressBook privacy class; a host app built without the AddressBook entitlement is refused there with no prompt, and no package-side change can alter that. Calendar has the same split (sqlite reads of `Calendar.sqlitedb` need Full Disk Access; writes go through Calendar.app and EventKit, gated by the calendars privacy class). The attribution guidance shows when the target app is installed but macOS still refused the Apple event, the signature of running under a parent that cannot be granted Automation (a foreign shell, an embedded terminal, a host app) rather than a broken install. Mail writes are gated by Automation to Mail for the responsible process and show only for a hard deny; `dry_run` never sends Apple events to Mail. Mail body paste for `mail_send` and `mail_draft` uses System Events, which needs Accessibility, not Mail Automation (-1743); a sticky "Don't Allow" for node to System Events means the Allow dialog will not reappear and the operator must flip the Automation row and re-run `permissions`; missing System Events GUI scripting is not a Mail send hang. Mail send timeouts: clients must Sent-check before retrying a send, because a retry of a delivered send creates a second copy; it is not a silent TCC grant. Messages writes are a separate Automation target from Mail, Contacts and Calendar.
- `runAppleScript` normalizes the result (`ok`, `output`, `error`, `kind`) and takes `appName` so a refusal can be told apart from a missing app. First-party apps live in `/System/Applications` on Ventura and later (standard install locations are checked).
- `DATE_HANDLER` builds a local `date` from validated integers and resets the day to 1 first, so setting the month never rolls the date forward (Jan 31 would become "Feb 31"). Date parsing for writes is strict: writes never guess, only explicit local datetimes are accepted (`YYYY-MM-DD`, `YYYY-MM-DD HH:MM`, `YYYY-MM-DDTHH:MM[:SS]`), so an agent cannot silently schedule "next tuesday" against the wrong day, and impossible calendar days such as 2026-02-31 are rejected.

## `lib/audit.js`

- The audit compares the vector index against the source data with zero tolerance: every source item is checked with no date filtering (except the same `APPLE_TOOLS_INDEX_DAYS_BACK` cap the indexer applies to email), and it only reports; it never fixes. It is built for 100,000 or more items.
- To count the same things the indexer indexes, it mirrors the indexer: email files are `*.emlx` outside the excluded folders (Junk, Saved Junk, Trash, Deleted Messages), calendar events use the indexer's 10 year window and are counted only when they have occurrences, so database junk (far-future placeholders, deleted events) is not counted. Message rows need `text` or `attributedBody`. Event ids are the bare `dbId`, with no timestamp, to match the indexer's id format. Calendar IDs use `CalendarItem` with `GROUP BY`, as the indexer does.
- Only the id field is fetched from LanceDB for the ID sets (performance). Messages have no orphaned entries, since the database persists; calendar is checked in reverse (`findMissing(indexedIds, sourceIds)`) for stale entries, and email orphans come from `findOrphaned` with an existence check.
- Email headers are read like `indexer.js` does it: the Apple Mail envelope's byte count line is stripped to reach the RFC822 content, and regex extraction handles folded headers, case differences and optional whitespace. A metadata read that fails is silent, because the audit still reports the item.
- Email duplicates: a missing file whose Message-ID matches an indexed email is a deduplicated IMAP copy, not a missing item. It is counted in the summary, not listed one by one, and the report shows coverage adjusted for deduplication separately from truly missing items. The three sources are audited in parallel.

## `lib/calendarWrite.js`

- Events are addressed by their iCalendar UID (Calendar.app's `uid`), which `calendar_date` reports as "Event ID" and `calendar_add` returns. Alerts are minutes before the start, at most four weeks (`MAX_ALERT_MINUTES` 40,320). An RRULE is built from structured arguments (`FREQ` daily, weekly, monthly or yearly with optional `INTERVAL`, `COUNT` or `UNTIL`, and `BYDAY` for weekly) or a raw rule is validated; `UNTIL` is in UTC per RFC 5545. With only a start, an all-day event ends at the end of that day and a timed event runs an hour (rolling into the next day late in the evening).
- `CALENDAR_FIND_TIMEOUT_MS` is 45 seconds, below the MCP client SDK's own default 60 second `CallTool` timeout. Regression found 2026-09-23: `calendar_edit`'s classic AppleScript fallback and `calendar_rsvp` ran `atmFindEvent` under a flat 60,000 ms timeout, so the client could give up with a raw "Request timed out" before the server answered, even though the operation kept running and usually succeeded (the same class of bug already fixed for `mail_send`, reply and forward). The margin also covers `atmFindEvent`'s own retry loop (about 8 seconds worst case). No test pins this value (the mail timeouts are pinned against `MCP_CALL_DEADLINE_MS` in `tests/unit/write-tools.test.js`, the calendar one is not).
- `atmFindEvent` retries the classic lookup a few times. Regression found 2026-09-23: RSVPing to an event created moments earlier through the daemon's separate EventKit session failed with "no event with that id was found" on the first lookup although the event existed, because Calendar.app's classic AppleScript object model can lag behind a write made through EventKit. An EventKit based fix is not available here: writeOnly EventKit can only re-query an event through the exact in-memory `EKEvent` from the session that created it, which does not exist for a real invitation synced in from elsewhere.
- Delete: Calendar.app has no `remove` or `move to trash`, only `delete`. Delete through the AppleScript event `id` inside the owning calendar. Never `delete (every event whose uid ...)`: that specifier hangs on iCloud and CalDAV, and the 60 second `spawnSync` timeout was then classified as TCC. A detached `delete theEvent` after `atmFindEvent` is also wrong (-1728). Lookup errors are not swallowed: a failed delete must surface, then EventKit can run. `calendar_remove` must never hide the AppleEvent code behind TCC copy (Mini `--apply` showed add and edit PASS then remove FAIL looking like a TCC deny, because `failure()` dropped stderr when the classifier mapped ETIMEDOUT or -1712 to tcc; same write bridge RPC as add and edit, not a different calendar account).
- A non-recurring add must not fall through to Calendar.app: on the Mini, writeOnly EventKit cannot delete AppleScript-created events and the Calendar.app delete hangs (ETIMEDOUT), so it fails closed with the EventKit code. Mini EventKit `status=4` is writeOnly: it can create and delete events this process saved, but `calendarItemsWithExternalIdentifier` cannot see an event Calendar.app created through AppleScript, so add and remove are aligned by creating through EventKit and deleting with the same identifiers (`calendarItemExternalIdentifier` and `eventIdentifier`). When EventKit add failed (likely writeOnly cannot list calendars) the code once silently created through Calendar.app, and the later remove then returned `EVENTKIT_NOT_FOUND status=4` plus a Calendar.app delete ETIMEDOUT: no AppleScript fallback for non-recurring creates. Creation is one-shot: return the identifiers from the saved `EKEvent` and do not re-query, since writeOnly `status=4` cannot `eventWithIdentifier` after save.
- JXA prints an `NSString` as `[id NSTaggedPointerString]` if you `String(title)`, so the title match failed even with one EventKit calendar; always `ObjC.unwrap` or `.js`. The EventKit id is `calendarUUID:eventUUID`: look up the compound id and each half so `eventWithIdentifier` and the external identifier both get a usable string. For a lookup, prefer the EventKit session that cached the `EKEvent` from create; the one-shot lookup is a full-access fallback.
- Listing calendars: EventKit does not need Calendar.app running, so a real EventKit list can stand in when the classic path fails (app closed); an empty EventKit string is not that list, because the JXA helper once swallowed every error and still exited 0, hiding TCC, timeout and not-running.
- Calendar.app's AppleScript dictionary defines `participation status` as one of `unknown`, `accepted`, `declined`, `tentative` (confirmed with `sdef` and the aete dump). There is no "needs action" term: that bare two-word phrase was a syntax error (AppleScript parsed "needs" as an identifier and failed at "action" where it expected "then"). `unknown` means no answer yet. Some macOS versions refuse to write the status from AppleScript, and the tool reports the refusal instead of silently doing nothing.
- The first-run and upgrade probe is a live Calendar.app Apple Event that triggers Automation to Calendar; it only lists, creating no events, so nothing is left behind, and it is not a `dry_run`.

## `lib/config.js`

- The config path is fixed at `~/.apple-tools-mcp/config.json` (or under `$HOME`). Paths inside the config contents are ignored: config is data, not instructions or path overrides, and the data directory (config, `indexer.lock`, `vector-index`) is always under the user's home.
- Index interval precedence, highest first: `INDEX_INTERVAL_MS` environment variable, then `indexInterval` or `indexIntervalMs` in `config.json`, then the product default of 5 minutes (the MacBook and MCP local fallback default). Values are clamped to 15 seconds through 6 hours (30 seconds stays allowed); human forms such as `500ms`, `30s`, `1m` and `1h` are accepted. Invalid input yields the default (not the minimum). The recommended Mini always-on value is 1 minute, set in `config.json`, not the product default. A missing config file is fine, and invalid JSON does not throw: callers get empty data plus a warning. The interval is resolved once at process start and logged once, in human form and milliseconds.
- `--transport=http` binds to `127.0.0.1` port 8421 by default: network exposure is opt-in. Precedence for host and port: environment variables, then `config.json`, then the default.

## `lib/contactsWrite.js`

- Contacts are addressed by their AddressBook unique id (Contacts.app's `id`, for example `ABCD1234-...:ABPerson`), which `contacts_search` and `contacts_lookup` report as "Contact ID" and `contacts_add` returns. Writes go through Contacts.app rather than the AddressBook sqlite file, because writing that database directly corrupts iCloud sync.
- A cold `tell application "Contacts"` under launchd often returns -600 instead of auto-launching. The ensure step runs `open -a Contacts` in this process (the write bridge daemon when routed), then `launch` (not `activate`, which waits until Contacts is frontmost and a slow cold start can ETIMEDOUT and must not abort the ready poll as TCC), then polls until a trivial AppleScript (`get name`) responds. A launch or ready ETIMEDOUT is a slow cold start, not Automation, so it keeps polling. A wall clock budget (`CONTACTS_READY_BUDGET_MS`, 20 seconds, with a 4 second launch and 2 second ready script timeout) keeps ensure plus CRUD under the 90 second write bridge timeout.
- Dropping every email or phone is destructive, so it needs confirmation. The first-run and upgrade probe creates a clearly named throwaway person and deletes it in the same script so a finished run leaves no junk, with a best effort cleanup if it created the person and then failed mid-script; it is a live Apple Events check, not a `dry_run`.

## `lib/eventKitSession.js`

- A long-lived EventKit JXA worker, kept by the indexer daemon as one `osascript` process. A writeOnly grant (`EKAuthorizationStatus` 4) can create an `EKEvent` and read identifiers off that in-memory object, but cannot re-query through `eventWithIdentifier` or `calendarItemsWithExternalIdentifier`: Mini commit 2cdf44d failed an add on a post-save lookup even though create had returned ids. So `create` caches the `EKEvent` objects, `update` and `remove` use the cache to call `saveEvent` and `removeEvent` without a fetch, and `create` never calls `findEventByIds`.
- Protocol: the parent writes one JSON command to `cmd.json` and polls `rsp.json` for the JSON reply (the worker reads and writes the same files); the child's stdin and stdout are ignored. `spawn` runs with `shell: false`, so nothing is interpolated into a shell. Cleanup of the command and response files and the child is best effort: a failed `unlink`, `kill` or `quit` is ignored.

## `lib/httpAuth.js` and `lib/httpTransport.js`

- stdio needs no auth, since a locally spawned child is trusted by whoever spawned it. HTTP is reachable over the LAN and, through Tailscale, from outside it, and the server exposes write tools (send iMessage, edit contacts and calendar), so every HTTP request must carry a bearer token (guard: `tests/unit/http-auth.test.js`).
- The token is a random secret generated once and stored in the macOS Keychain, never in a config file, the repo, argv or logs. It is printed only by the explicit `http-token` command. There is no external account, OAuth flow or cost: it is a self-issued password, like an SSH key.
- Under a secrets manager's runtime injection (`infisical run`), `APPLE_TOOLS_HTTP_TOKEN` carries the token instead and the Keychain is neither read nor written. During a rotation `APPLE_TOOLS_HTTP_TOKEN_PREVIOUS` is also accepted, so clients still on the old token keep working until they switch; unset it to retire the old token. The previous token is honored only when the current token itself came from the environment.
- The bearer check is constant time and checks every accepted token with no early exit, so timing does not reveal which one matched; it never throws.
- `lib/httpTransport.js` is separate from `index.js` so request parsing and authorization can be exercised without starting the MCP server or touching the Keychain (guard: `tests/unit/http-transport.test.js`). The request target is relative, and no URL base is derived from the user-controlled `Host` header, which can itself be malformed.

## `lib/indexGate.js`

- `sessionIndexComplete` means "this process finished (or abandoned) its own index cycle". A second MCP instance that lost the indexer lock never runs a cycle, so that flag stays false, and lost-lock must not be treated as "still indexing": callers still check `isIndexReady()` for a missing index. `isIndexReady()` and `initDB()` re-list the LanceDB tables on each check so a first empty catalog (daemon writer in flight) is not cached forever. After a cycle or rebuild ends, searches are unblocked on success and on failure (guard: `tests/unit/index-gate.test.js`).
- The "table missing" message is distinct from still-indexing: retry because the index is not there yet, not because this process is mid-cycle. The still-indexing copy is only for a process that owns the lock and has not finished a local cycle, never for a lost-lock MCP reader, which never gets "building initial index".
- A shared index older than `STALE_INDEX_INTERVALS` (3) refresh intervals gets a note, and the index is never called stale sooner than `STALE_INDEX_FLOOR_MS` (15 minutes), whatever the interval. The reason comes from who holds `indexer.lock`: a live holder that keeps checking in is still working (a rebuild, a long first pass, or catching up after the Mac slept). The HTTP server never indexes (3.4.1), so with the indexer daemon down it would otherwise serve a stale index silently. With no finished pass on record the note stays silent through normal warm-up and speaks only once a regular pass has finished with every source read skipped (`lastSkippedPassTime`): the index has then never refreshed. The lock-holder read runs only once the index is stale, and a throw words the note as "may be down".

## `lib/indexMaintenance.js`

- Upkeep for the long-lived daemon. `createIndexedIdCache` keeps the indexed ID sets (email `filePath` and `messageId`, message id) in memory and re-reads a table only when its LanceDB version moved, so a quiet pass costs one version check instead of a full column scan. After the process adds rows (right after a `table.add()` whose sets were read with `getIdSets` just before), it folds them into the cache; if the table moved by anything other than that one commit (another writer), the entry is dropped and the next read re-reads.
- `createDuplicatePathTracker` remembers email files skipped because their Message-ID is already indexed (IMAP copies in another folder), so they are not parsed again every pass; `retainOnly()` drops paths that left the incremental lookback window, so the set stays bounded by the window's duplicates.
- Compaction and old-version cleanup (`optimizeIndexTables`) run at most daily (`INDEX_OPTIMIZE_INTERVAL_MS`, 24 hours), only after a pass that wrote something, keeping one hour of table history (`INDEX_OPTIMIZE_KEEP_VERSIONS_MS`). Failures are logged per table and never thrown: an index pass must not fail because upkeep did. A last-optimize time in the future counts as due.

## `lib/indexerLock.js`

- `indexer.lock` acquire, release and heartbeat. A live holder is never displaced, even if the lock timestamp is old (a blocked event loop, a long index cycle). Dead-PID takeover never renames the live lock path: waiters take a `wx` mutex, re-read, unlink only if the contents are still the expected dead lock, `wx`-create the new lock, then drop the mutex, so a peer's freshly created lock is never deleted (re-read immediately before unlink). An orphaned takeover mutex is never stolen with compare-then-unlink of the live `.takeover` path: waiters `wx` a fence named by the dead PID. Empty or unparsable mutex or lock contents are unknown, so nothing is fenced or stolen (this covers the `wx` open-then-write and heartbeat truncate-then-write windows). A failed heartbeat write is retried by the next heartbeat or cycle. Guard: `tests/unit/indexer-lock.test.js`.
- `readIndexerLockHolder` is for readers that never take the lock (the HTTP server, lost-lock stdio clients): read only, never writes or removes anything. A holder whose heartbeat is older than `LOCK_HOLDER_FRESH_MS` (5 heartbeats) has stopped checking in.

## `lib/indexerRuntime.js`

- Kept separate from `index.js` so daemon paths can be tested without starting MCP stdio or loading the embedding model. The stdin `close` handler binds only for MCP stdio clients; indexer daemons ignore it (LaunchAgent often uses `/dev/null`).
- In-flight tracking (guard: `tests/unit/stdio-drain-on-close.test.js`): a caller that pipes a batch and closes stdin (`printf ... | apple-tools-mcp`) fires stdin `close` right after the last line is read, while `tools/call` is still running; without tracking the close handler exits mid-call. It must be called after `server.connect(transport)`, since the Protocol sets `onmessage` there. The SDK sends no response for a cancelled request. On close the process lets in-flight requests answer (up to `timeoutMs`) and then exits; exiting synchronously drops the last `tools/call`, and the SDK's `send()` resolves only once stdout has drained, so an answered request is fully written.
- After a cycle the daemon keeps the lock and the MCP local fallback releases it. MCP startup: stdio indexes locally only when the lock is free. The HTTP server never takes `indexer.lock`: it serves the shared index the daemon keeps fresh, and as a local fallback it could win the lock while the daemon restarted after an install, leaving the daemon waiting for it. Once a process owns the lock, heartbeat plus background cycles is the one shared path, and the MCP local fallback uses it too, not only the daemon. The daemon retries until it owns the lock, then runs its setup.

## `lib/keychainWrite.js`

- The `security` utility parses one stdin line, so credential bytes never enter process argv. Apple's interactive command buffer is 4096 bytes, so an over-long value is rejected before any truncated write (guard: `tests/unit/keychain-write.test.js`).

## `lib/httpStdioProxy.js`

- Forwards the tool interface from an HTTP MCP server to a local stdio client (`apple-tools-http-proxy`).

## `lib/lancedbTables.js`

- The MCP stdio server and the indexer daemon are separate processes, and the daemon holds a writer connection for its lifetime. A short-lived MCP reader must still see the on-disk `emails`, `messages` and `calendar` tables, including when its first connect listed an empty catalog (writer commit in flight, a stale snapshot, or a concurrent `initDB` that returned before `openTable` finished). Default LanceDB consistency does not re-check other processes, so readers pass `readConsistencyInterval: 0` (`LANCE_CONNECT_OPTIONS`) so `tableNames()` and `openTable()` see the committed catalog. Guard: `tests/unit/mcp-shared-index.test.js`.
- Cache caps: without a Session every connection gets the library defaults, a 6 GB index cache and a 1 GB metadata cache. The indexer daemon runs for days and fills them, so both are capped (64 MB and 256 MB by default, `APPLE_TOOLS_LANCE_INDEX_CACHE_MB` and `APPLE_TOOLS_LANCE_METADATA_CACHE_MB` override, anything that is not a whole number from 1 to 8192 falls back to the default). `createLanceSession` takes lancedb's `Session` class as an argument so this module never imports the native package. Guard: `tests/unit/index-maintenance.test.js`.
- LanceDB stores each table as `<name>.lance` under the index directory; `lanceTableExistsOnDisk` checks that path.
- `openMissingIndexTables` always re-lists `tableNames`; a prior empty catalog is never assumed final. When a table is on disk but unlisted it drops every cached handle and reconnects once. Every step re-checks `isCurrent`, so a `reset` during a slow connect aborts the stale work.
- `createLanceTableCache`: `tables` is one stable object (`reset` deletes its keys and never replaces it) so `indexer.js` can alias it for `createTable` and `dropTable` mutation. A connect that finished after a `reset` closes its stale connection and connects again.
- Pending promises are stored as the `.finally()` chain (`rememberPromise`), not the raw promise. Discarding the derived promise turns a failed `connect()` into an `unhandledRejection`, which makes `index.js` exit. Guard: `tests/unit/mcp-shared-index.test.js`, "failed connect rejects to the caller without an unhandledRejection".
- Errors from closing a stale or reset connection are ignored on purpose.

## `lib/mailFind.js`

- `mail_find` answers "which messages match these exact facts" (subject prefix, sender, sender display name, recipient, mailbox, date) from Mail's own Envelope Index, with no vector index. Bulk `mail_trash` uses `locateMessageCopies` to address every copy of a Message-ID by Mail's internal id.
- A message's AppleScript `id` is its Envelope Index ROWID, so `messages of <one mailbox> whose id is N` resolves in about 2 s even on a 60k-message INBOX, where `whose message id is X` across every mailbox takes 30 to 38 s (the reason for `MAIL_FIND_TIMEOUT_MS` in `lib/mailWrite.js`).
- Read only: sqlite3 opens the database with `-readonly` and Mail stays its only writer. It needs the same Full Disk Access as the .emlx indexer.
- Mailbox leaf names per kind are the names Mail uses across iCloud, IMAP, Exchange and Gmail. A mailbox URL such as `imap://<account uuid>/Sent%20Messages` decodes to an account id plus a mailbox path; local "On My Mac" mailboxes have no account id and cannot be addressed by `account id` in AppleScript.
- The sender display name is stored decoded (RFC 2047) in `addresses.comment`, and `LIKE` is case-insensitive for ASCII. "Me" (`fromMe`) means any address that is the sender of a message in a Sent mailbox.
- The query selects limit plus one rows so truncation can be detected. Every copy is its own row: the same Message-ID in INBOX and Sent shows twice. `locateMessageCopies` splits every live copy into copies outside Trash (to move) and ids with no such copy (already trashed or not in Mail).
- `mail_find` throws on invalid arguments or an unreadable index and returns text.

## `lib/mailIdempotency.js`

- Send claims are cross-process and restart safe, and only hashes and outcome metadata are stored. A crash or a corrupt record fails closed, including an empty file left between exclusive creation and its first write. No uncertain claim ever expires: a missing Sent row cannot prove a queued send will not run later.

## `lib/mailLinks.js`

- `mail_read` strips HTML, which drops every link target, and reads the .emlx without MIME decoding, so a quoted-printable URL comes back broken across soft line breaks. Sign-in emails (magic links, confirm links) put the one thing a caller needs behind an `<a href>`. `mail_links` reads the message file Mail keeps for the id `mail_find` returns, decodes its MIME parts (multipart, quoted-printable, base64, charset) and returns each http(s) link with its visible text. Read only, with the same Full Disk Access as `mail_find`. Guard: `tests/unit/mail-links.test.js`.
- An .emlx starts with a line holding the byte count, and a plist trails the message. Links are scanned without regex backtracking. An unclosed anchor's text runs to the next anchor or the end. HTML anchors come first, then plain-text URLs not already listed.
- Mail shards its folders by message id: id 73690 lives under `Data/3/7/Messages` (the digits of id divided by 1000, reversed). Account mailboxes live under `V<n>/<account id>/` and On My Mac mailboxes without an account id under `V<n>/Mailboxes/`. `mailboxFound` tells a caller "not saved yet" (worth retrying) from "cannot locate this mailbox" (not).
- It throws on invalid arguments or an unreadable index and returns JSON text.

## `lib/mailWrite.js`

- Messages are addressed by RFC822 Message-ID (Mail's `message id` property). A `file_path` from `mail_search` or `mail_recent` is also accepted and resolved to a Message-ID by reading the .emlx headers, so callers never invent an identifier. The AppleScript locator checks the inbox first, then every mailbox of every account.
- A real send is not success until Sent or Outbox is checked: AppleScript `send` returning without a throw is not enough. A message already in Sent or still in Outbox is success and never a TCC failure. Hang recovery matches To plus subject (and Message-ID when known), never the subject alone, because short subjects such as "test" are unsafe. `ETIMEDOUT` and -1712 are timeouts (also for find, reply and open before the send); -1743 and -10004 are a hard deny, and a timeout is never labeled TCC. A hard deny is recognized by `isMailHardTcc` (a classified kind of `tcc`, or an error matching `HARD_TCC_SIGNATURES` in `lib/appleScript.js`: -1743, -10004, -25211 and "not authorized" or "not allowed" Apple events text). `recoverIfInSent` returns no hit when its Sent or Outbox check fails or has no time left: a failed check is never treated as delivered.
- Ship gate probe: the compose verb that hangs when node to Mail Automation is denied is `make new outgoing message`. `tell Mail to get name` is not enough, because on the Mini it returned while compose blocked. Nothing is sent and the outgoing message is deleted at once. The live Apple Events check is not a `dry_run`, which never talks to Mail.
- System Events probes: `tell application "System Events" to get name` can soft-pass, so it is only the cheap pre-compose check (`MAIL_SE_PROBE_TIMEOUT_MS`, SIGKILL on a hang) and never the `permissions` grant. A Mini reported granted while TCC `auth_value` was 0 for node to `com.apple.systemevents`, so the permissions probe uses process or GUI scripting (`tell process`), which is the grant `mail_send` needs. Its timeout (`SYSTEM_EVENTS_AUTOMATION_PROBE_TIMEOUT_MS`) is long enough for the operator to click Allow, with no short inner AppleEvent timeout, like the compose probe. It never types into the focused UI. Guard: `tests/unit/write-tools.test.js` ("bounds compose Apple events and SIGKILLs hung osascript", and the assertion that the permissions timeout is longer than `MAIL_SE_PROBE_TIMEOUT_MS`).
- Sentinels: `BODY_FOCUS_UNPROVEN` means the focus request ran but the re-read `AXFocusedUIElement` was not the chosen body. `DISPLAY_ASLEEP_GUI_UNAVAILABLE` means System Events sees 0 Mail windows while Mail AppleScript still lists the compose, because the screen saver is up (loginwindow owns the screen) or the display is asleep. A Mail To: recipient chip surfaces as U+FFFC (character id 65532), not body text. The marker constants let tests pin the proven path (`ATM_AX_HIT_TEST_MARKER` for the JXA hit test, `SYSTEM_EVENTS_AUTOMATION_PROBE_MARKER` for the permissions-only probe).
- Display wake: `wakeDisplay` declares user activity so a sleeping display wakes before GUI scripting. `DISPLAY_WAKE_SECONDS` outlasts the whole compose osascript (`MAIL_COMPOSE_TIMEOUT_MS`) so the caffeinate assertion is live while it runs. `caffeinate` runs detached for its own `-t`: a blocking spawn would either SIGKILL it early (a 5 s timeout cut the 15 s assertion at about 4 s) or release it before compose starts. It does not dismiss a running screen saver (the compose script does that), is best effort and never throws. Guards: `tests/unit/write-tools.test.js` ("wakes with a detached caffeinate that outlasts the compose") and `tests/unit/shell-detached.test.js`.
- Body location: the compose body is the AX element taller than `MAIL_BODY_MIN_AX_HEIGHT` (the To, Subject and Cc fields are about 22 px), which rejects short header text areas without walking windows. `MAIL_BODY_TAB_MAX` is a historical Tab count; the body is found by title marker plus AX hit test, not Tab. `MAIL_BODY_START_KEY_CODE` is Command-Up (start of document), which reply and forward prepend use instead of Cmd-A so the quoted original stays. Mail window titles may truncate, so `MAIL_COMPOSE_TITLE_MARKER_MAX` leading subject characters are matched. `MAIL_COMPOSE_TOP_UI_MAX` bounds the top-level `UI elements` of process Mail, never a deep tree walk.
- Timeouts: `MAIL_COMPOSE_TIMEOUT_MS` (make, keystroke and send) is far below the roughly 60 s System Events wedge. `atmFindMessage`'s `messages of <box> whose message id is X` scan is slow on a large mailbox (30 to 38 s observed on a mailbox of about 68,500 messages, even when the match is in the first box checked; a known AppleScript `whose` filter trait, not one mailbox's). `mail_mark`, `mail_archive` and `mail_trash` once had no explicit timeout and used the shared 30 s default, so they timed out before the scan finished. `MAIL_FIND_TIMEOUT_MS` (50 s) leaves real margin over the observed worst case and stays under the MCP client SDK's default 60 s CallTool timeout. `MCP_CALL_DEADLINE_MS` (55 s) is the whole tool call, leaving the process time to format its answer. `mail_reply` and `mail_forward` run `atmFindMessage` and then the send inside one osascript, so a budget at the 38 s find ceiling would kill the script before the send; `MAIL_FIND_AND_SEND_TIMEOUT_MS` matches the find only budget, which leaves about 12 s for the send after a 38 s lookup, and verification afterward is capped to whatever is left under `MCP_CALL_DEADLINE_MS`, not a second full window. Guard: `tests/unit/write-tools.test.js` (the assertions on `MAIL_FIND_AND_SEND_TIMEOUT_MS` and `MCP_CALL_DEADLINE_MS`).
- Sent verification budget: six consecutive real sends on an iCloud/IMAP account all delivered, but each took a different unbounded time before Mail made the message queryable in Sent (20 s, 20 s, 30 s, 65 s, 47 s and about 64 s observed) even though `send` returned in a few seconds. The old budget (3 attempts of 400 ms) gave up long before that and reported a false failure for mail that was delivered. A bigger budget alone cannot fix it: the MCP client SDK's default CallTool timeout is 60 s (McpError -32001), and a 30 attempt, 4 s budget (about 120 s worst case) tested against a real client made the client give up while the server was about to find the delivered message. Any purely synchronous verification longer than that ceiling is self-defeating, so `SENT_VERIFY_ATTEMPTS` and `SENT_VERIFY_RETRY_MS` stay under it and a miss within budget is reported as unconfirmed, not failed (9 of 9 real sends observed eventually succeeded). Attempts and sleep are a ceiling, not a guaranteed wait: each poll also runs under `SENT_VERIFY_TIMEOUT_MS` (15 s), so 6 polls of 15 s plus the sleeps could pass the 60 s client timeout if a poll hung, so `verifyQueuedMessage` stops at `MCP_CALL_DEADLINE_MS` and shrinks each poll to the time left, and `SENT_VERIFY_MIN_POLL_MS` skips a poll that could not return before the deadline. Guard: `tests/unit/write-tools.test.js` (`SENT_VERIFY_ATTEMPTS` call count).
- Older hang recovery scripts returned `FOUND` to mean Sent; `SENT_VERIFY_FOUND` is still accepted. Tests can skip the retry delay without changing the attempt count.
- AppleScript on macOS 26.x: ordinal and keyword tokens fail to compile in `set {a, b}` lists (MacBook 26.1 and Mini 26.6.2: `th` gives -2741), so `ATM_APPLESCRIPT_RESERVED_SHORTS` lists names paste focus handlers must not destructure into (guard: `tests/unit/write-tools.test.js` and `tests/indexing/security/applescript-injection.test.js`). System Events rejects the compound `focused UI element` (MacBook 26.1 compile -2741, Mini 26.6.2 compile -2740), the same class of dictionary break as bare `web area`, so `buildAtmFocusedElementHandler` reads `AXFocusedUIElement` first (nested caret) and falls back to `first UI element whose focused is true`, which is the compile proven path. A process level `whose` match can be the key window, so callers must still reject header roles and AXWindow. Guards: the `not.toMatch(/\bfocused UI element\b/)` assertions in `tests/unit/write-tools.test.js`.
- Native compose body (`composeNativeBody`) is keystroke or paste, not AppleScript content. HTML is tag stripped so `<p>...</p>` becomes typed text. It never prefixes lines with `>` and never emits `<blockquote>`, because AppleScript `content` and `html content` cite-wrap them (Ventura and later, FB11734014). Mail's `mailto` command is not used: on current Mini and MacBook Mail it does not return an outgoing message (`newMessage` stays undefined, AppleScript -2753), so the script always does `make new outgoing message` with no `content:`. Guard: `tests/unit/write-tools.test.js`, "mail compose native paste (FB11734014, -2753)".
- The body needle is a distinctive first line, because a full multiline `contains` can miss when Mail stores an HTML alternative. The compose window is found by subject fragment among top-level System Events UI elements: Mail's window title is the subject after `make new outgoing message`, and empty drafts show "New Message".
- Optional coordinate finder: kept off the compose delivery path. An earlier version called it and treated an empty AXValue as OK, so the keystroke recovery never ran (AXValue writes are a silent no-op). The delivery path uses no `AXUIElementSetAttributeValue`, no click, and treats an empty value as not success.
- Body delivery handlers: find the compose window by exact subject title (`name of` windows, then the top-level exact title fallback when `windows` is empty), find the body by walking `entire contents` of that window and taking the first `AXWebArea`, focus it with System Events `set focused of <AXWebArea> to true` (not `set value`, not `AXUIElementSetAttributeValue`), re-read process `AXFocusedUIElement` and require role `AXWebArea` plus the same position and size. A mismatch is `BODY_FOCUS_UNPROVEN` (the draft is deleted and nothing is sent); a missing window or body is `BODY_FOCUS_FAILED`. Delivery is clipboard paste: compose passes `replaceBody=true` (Cmd-A, then paste); reply and forward pass false (Command-Up to the top, then paste) so the quoted original stays. No coordinate click, no Mail `content` or `html content`, and no Mail `content of` oracle (it stays empty on Mail 16 and macOS 26). AXTitle reads in the title helpers stay inside `tell application "System Events"` (outside it they failed osacompile with -2741). Recipients and subject are AppleScript properties and are never pasted. The body needle check runs only when the focused element is still the proven body, so a To: U+FFFC chip is not `BODY_PASTE_MISDIRECTED`. Header checks stay. The proof that the body landed is the Sent .emlx after send. Guards: `tests/unit/write-tools.test.js` (the `BODY_FOCUS_UNPROVEN` ordering assertions).
- Reply, forward and compose matching in Sent and Outbox: proper Mail replies set In-Reply-To, but the fallback `make new outgoing message` path does not, so a reply also matches an exact "Re: " plus the original subject, and never the original itself or a Re: that merely contains the original subject. Mail.app forwards do not set In-Reply-To or References (those headers mean replies), so a forward needs the intended recipient plus either an exact Fwd: or Fw: subject or the original Message-ID in the forwarded body, and skips the original, In-Reply-To hits and unrelated Fwd: mail that only shares a To. A compose match needs To plus subject, and prefers Message-ID with To when known; the old subject only matcher is deprecated because it cannot hit without recipients.
- Finishing a compose, reply or forward (`deliverySummary` and the verify steps before it): a send hang is not labeled TCC, and if Mail already delivered the result is success; a hard -1743 or -10004 stays a deny.
- A draft is not delivery, so it does not need multi-recipient confirmation (`recipientCount` is 0). `reply_all` fans out to every original recipient, so it counts as a multi-recipient send and requires confirmation.
- Reply and forward intro text pasted above the quote ends with a newline so the note does not glue to "On ... wrote:". Its needle still comes from `composeBodyNeedle`. The prepend uses the visible window title from the live subject, no Cmd-A, and no AppleScript `content`: Mail 16 on macOS 26 leaves `set content` empty, which is why reply and forward once sent a blank intro.
- Bulk `mail_trash` (`MAIL_BULK_TRASH_BUDGET_SEC`, 35 s) stops starting new moves so the call answers inside `MCP_CALL_DEADLINE_MS`. Each copy takes about 2 s (one `whose id is` lookup in its own mailbox, then the move), and callers re-run for whatever is left. The script is one osascript for every copy: each copy is found by Mail's internal id in its own mailbox and moved only if its Message-ID still matches, so a stale Envelope Index row can never move the wrong message. Output is one `<id>\t<status>` line per copy with status moved, missing, mismatch, no_account, no_trash, skipped (time budget) or `error <n>`. `mail_trash` with `message_ids` moves every copy (INBOX, Sent, Archive and others) of each message to its account's Trash.
- `mail_unjunk` moves the Junk copies of `message_ids` (from `mail_find`) to each account's Inbox (the Inbox names Mail uses are tried in order). A copy is moved only if its Message-ID still matches and, with a name guard, the sender's display name (decoded by Mail) still contains the guard text (AppleScript compares ignoring case). Statuses are moved, missing, mismatch, name_mismatch, no_account, no_inbox, skipped or `error <n>`. Copies anywhere else are never touched and nothing is deleted, marked or sent. It is not destructive (Inbox is where mail lands), so it needs no confirm, and `dry_run` previews.

## `lib/messageContact.js`

- Indexed Messages rows carry raw handles: `sender` is a phone or email (or "Me"), and `chatIdentifier` is the other party's handle in a 1:1 chat or "chatNNN" for a group. Tool output shows contact names, so callers pass names back ("Dad"); these helpers map a name to handles and say who a from-me row went to. Lookups are injected so the logic is testable without the AddressBook. Guard: `tests/unit/message-contact.test.js`.

There is no fuzzy name matching: a short name must not pull in other people's threads.
- `describeMessagePeer` names the other side of a from-me row so "Me" lines say who they went to, for example `Dad (+12025550101)` or `group chat "Family"`, or null.

## `lib/messagesWrite.js`

- `to` is a phone number in E.164 form or an Apple ID email, one or more (more than one requires confirmation). `chat_id` is an existing chat GUID from chat.db (`iMessage;-;+15551234567` for 1:1, `iMessage;+;chat123456789` for a group). The GUID is verified against chat.db (`lookupChat`, which also counts participants) before sending, so a made-up chat id is refused rather than silently delivered elsewhere.
- An attachment path must already exist on this host; the tool never creates files (`validateAttachmentPath`).
- `buildMessagesAutomationProbeScript` and `probeMessagesAutomation` are the ship-gate and first-run probe: the Messages Apple Events used before a send (enumerate accounts, read service type). `messages_send` with `dry_run` never talks to Messages, so a dry run proves nothing about the grant. Nothing is sent.

## `lib/noDashes.js`

- Mail and messages written for a person read as machine written when dashes are used as punctuation, so every mail and Messages write goes out under the owner's name with dashes rewritten before anything reaches Mail or Messages. An em dash, en dash or similar dash character becomes a comma (nothing at the start or end of a line, and "to" between two numbers); a hyphen (or two or three) with a space on each side becomes a comma. Hyphens inside names, identifiers, paths, URLs and dates are not punctuation and stay (`Alexa-Echo-MCP`, `v1.1.0`, `2026-11-10`). A hyphen at the start of a line (a list bullet, or the "-- " signature line) also stays. The patterns are linear time only because they run on tool input. Guard: `tests/unit/no-dashes.test.js`.
- `html: true` also rewrites `&mdash;` style entities. `findDashes` returns the lines that would change, for callers that refuse instead of rewriting. `DASH_FIELDS` lists the text fields of each write that goes out under the owner's name (subject and body for `mail_send` and `mail_draft`, body for `mail_reply` and `mail_forward`, text for `messages_send`); `withoutDashes` applies it to a tool's arguments.

## `lib/orphanWorker.js`

- The indexer daemon forks one index worker (`--mode=indexer --indexer-worker`) and keeps the write bridge in the parent. A worker with a free event loop exits on its own when the IPC channel closes. One with a blocked event loop (a stuck synchronous read) cannot, and launchd does not kill it either: when the job's main process dies it signals the rest of the process group but never escalates to SIGKILL (proved on the Mac mini). The orphan then keeps `indexer.lock` forever and the restarted daemon's new worker waits behind it.
- Only the `indexer.lock` holder is a candidate, and only when every check passes (`isOrphanedIndexWorker`): its parent is gone (re-parented to launchd, PID 1), it runs as this user, and its command line is an index worker's. Anything else (a stdio MCP client that won the lock, another daemon's live worker) is left alone. The worker never serves writes, so stopping it cannot start or repeat one. It gets SIGTERM, then SIGKILL after `ORPHAN_TERM_GRACE_MS`, and the process is checked again before the kill so a reused PID is never touched. Guard: `tests/unit/orphan-worker.test.js`.

## `lib/permissions.js`

- `apple-tools-mcp permissions` probes Contacts, Calendar, Mail, Messages and System Events under `process.execPath` so macOS can pop Allow dialogs for that node binary. The user clicks Allow; the command cannot grant silently. It always runs in this process, never through the write bridge, because the point is to attach the dialogs to `process.execPath`. If the invoked CLI, its shebang, sibling `node` or `argv[0]` points at a different node, it prints a loud WARN (`detectExecPathMismatch`, `formatExecPathMismatchWarn`) because Allows attach to `execPath`, not the path the user typed. Symlinks are collapsed to the real file (`normalizeNodePath`) so `.../bin/node` and its target count as the same binary.
- Mail and Messages use the existing live Apple Events helpers, since `dry_run` of `mail_send` or `messages_send` never talks to those apps and does not count. System Events uses process or GUI scripting (`tell process`), not a soft application `get name`, which can succeed without Apple Events authorization. `EXAMPLE_MINI_NODE` is the Mini ship-gate host example, not a universal path; `EXAMPLE_MACBOOK_NVM_NODE` is the current runtime binary and follows the selected Node installation.
- `classifyGrantStatus`: TCC, timeout and attribution on a live Apple Event mean a missing Allow. `exitCodeForGrants` fails closed: any required surface that is not granted is a non-zero exit. The Full Disk Access touch (`probeFullDiskAccess`) is advisory: read tools need it on this node, it is not one of the required Automation grants, and it never fails the command. Guard: `tests/unit/permissions.test.js`.

## `lib/processMode.js`

- Indexer: `node index.js --mode=indexer` is the canonical entry; `apple-tools-indexer` (`bin/apple-tools-indexer.js`) is detected by `argv[1]` or `--mode=indexer`. Permissions CLI: `apple-tools-mcp permissions` or `--mode=permissions`; `firstPositionalArg` skips flags (`--foo`, `--foo=bar`) so `node index.js permissions` and `apple-tools-mcp permissions` both resolve. Permissions is a short-lived CLI on the same bin and wins over indexer. HTTP transport: `node index.js --transport=http` or `apple-tools-http`; read-only versus write is unchanged, but every request needs a bearer token (`lib/httpAuth.js`). Token CLI: `apple-tools-mcp http-token` prints (generating if needed) the Keychain stored HTTP auth token, then exits. MCP stdio is the default when none of these is present. Guard: `tests/unit/process-mode.test.js`.

## `lib/shell.js`

- The module exists to prevent command injection: it uses `spawnSync` instead of `execSync` (no shell interpolation), passes arguments as arrays and validates inputs before execution. `shell: false` everywhere; `spawnCollect` never uses a shell either.
- `osascript`: the script goes as a `-e` argument (never a shell string). Hung Apple Events ignore SIGTERM (a roughly 60 s write bridge wedge on the Mini), so a timeout must SIGKILL osascript so compose fails fast instead of hanging. osascript may return non-zero for some operations, so stdout is returned if present and the call throws only when there is none.
- `safeFind`: partial permission errors can still yield some paths, and those are kept. A complete failure (no paths and a non-zero status) must not be taken as zero files, because callers persist index timestamps on empty scans. `maxBuffer` for `mdfind` is 100 MB for large result sets. Type is a single character and `mtime` is a format such as -1, +7 or 0 (validated).
- Async variants (`safeSqlite3JsonAsync`, `safeFindAsync`) exist for the indexer daemon: a slow query or a 2 minute find under heavy load waits without blocking the event loop, so the write bridge (`writer.sock`) keeps answering while an index cycle reads. Same validation, argv and error semantics as the sync versions. `spawnCollect` returns spawnSync shaped results (`stdout`, `stderr`, `status`, `error`): on timeout the child is SIGKILLed and `error` is an ETIMEDOUT Error like spawnSync's, and output past `maxBuffer` kills the child with ENOBUFS. It resolves and never rejects so callers keep sync semantics.
- `safeOpenApp` launches a first-party app with `open -a` (argv only, never a shell, only `OPEN_APP_ALLOWLIST`). Contacts cold start under launchd does not reliably auto-launch from `tell application "Contacts"`; `open -a Contacts` is the host-proven path.
- `safeSpawnDetached` starts a command in the background and returns at once (no shell, no timeout, stdio ignored). The child is detached and unref'd, so a spawnSync timeout never kills it mid-run and it never holds the caller open, which suits self-terminating helpers like `caffeinate -t N`. It returns the pid, or null if the spawn failed. Guard: `tests/unit/shell-detached.test.js`.

## `lib/urlQuery.js`

- Meeting links in calendar titles and locations often carry the join passcode in their query string (`zoom.us/j/123?pwd=...`). Calendar tools print each URL with its scheme, host and path only: the `?query` and `#fragment` are dropped (`stripUrlQueries`), so a passcode never reaches a chat that reads the calendar. A URL here is a scheme with `//` (`https://`, `zoommtg://`), a `www.` host, or a bare `host.tld/` path. The query runs to the next space, angle bracket or quote; a closing `)` or `]` at its end is kept, since it closes the text around the URL.
- Invite notes also carry passcodes as plain lines ("Passcode: 123456", "Meeting password: abc", "PIN: 123 456 789#", "PIN is 1234", Webex "Host key: 123456" and "Access code: 123 456", "Passcode 123456") and inside one-tap dial strings (`+15550100,,1000000001#,,,,*123456#`). `maskPasscodes` hides the value after a passcode label to the end of its line; a dial string keeps its digits up to the passcode and hides the passcode itself. A full-width colon (U+FF1A) counts as a colon. "PIN is" needs a value with a digit ("the pin is in the drawer" stays). A bare `,,1000000001#` is the meeting or conference ID, which the tools print like any meeting ID. "Passcode 123456" with no separator hides only a following token that has a digit. The comma run is bounded because an unbounded `,{2,}` is quadratic on a long run of commas. Guard: `tests/unit/url-query.test.js` ("stays fast on a long run of commas (no quadratic dial-string scan)").

## `lib/validators.js`

- The module centralizes input validation against path traversal, command injection, SQL injection and integer overflow. Guard: `tests/unit/validators.test.js`.
- `validateFilePath` checks the extension, resolves the path (so `../../../etc/passwd` is caught) and requires the result to sit inside the allowed directory. `validateLimit` (default 30, max 1000), `validateDaysBack` (max 3650, about 10 years) and `validateWeekOffset` (max 52) fall back or clamp so a caller can never ask for an overflowing or huge query.
- `escapeAppleScript` escapes backslashes first, then quotes, then line breaks. An unescaped CR or LF inside an AppleScript double-quoted string can close the string and inject more statements. `validateMailboxName` allows only letters, digits, a literal space, hyphen, underscore and period, and at most 100 characters; a literal space only, because `\s` would also allow newlines and tabs (injection risk). `escapeSQL` doubles single quotes and escapes backslashes; parameterized queries are preferred where possible. `validateLanceDBId` allows letters, digits, whitespace, hyphen, colon, comma and period, at most 500 characters. `validateDate` accepts only years 1990 to 2100.
- Regex safety: user input is never placed unescaped in a pattern (`escapeRegex`), and `safeMatch` and `safeReplace` truncate overly long input (10,000 and 50,000 characters by default) to prevent ReDoS. `stripHtmlTags` uses a small tag state machine instead of a regex (iterative, no ReDoS risk, and more predictable), replaces each tag with a space and normalizes whitespace (default limit 100,000).
- `MAC_ABSOLUTE_EPOCH` is 978307200 seconds: Mac epoch is 2001-01-01 00:00:00 UTC and Unix epoch is 1970-01-01 00:00:00 UTC. `macAbsoluteTimeToDate` accepts seconds or nanoseconds; a value above 50,000,000,000 is taken as nanoseconds (the Messages database uses nanoseconds): 5e10 seconds after 2001 is about the year 3585, far beyond any real seconds value, so a larger number must be nanoseconds. It returns Unix milliseconds as a number (not a Date), and 0 for null or NaN.
- `toUnixMillis`: Messages chat.db values are stored as seconds and email and calendar timestamps are milliseconds; treating seconds as milliseconds drops every date filtered message. The threshold 1e11 is 1973-03-03 in milliseconds, well before any real mail or message date, and far above Unix seconds for the year 2100 (about 4e9).
- `unfoldRfc822Headers` unfolds wrapped header lines (CRLF plus whitespace continuation) so From, Subject and To matchers see the full header value. `stripSubjectPrefixes` strips repeated Re:, Fwd: and Fw: prefixes for thread matching.

## `lib/writeBridge.js`

- Why it exists: macOS attributes an Apple event (and Contacts or Calendar access) to the responsible process of whoever sends it. When a host app spawns this server over stdio, the host, not node, is responsible, so a host without the Contacts or Calendars automation entitlement makes those writes fail regardless of node's own Full Disk Access. The indexer daemon is started by launchd, so node is responsible for its Apple events. The daemon therefore listens on a user-only unix socket and performs writes on behalf of stdio clients. Nothing leaves the machine: AF_UNIX socket, mode 0600, inside `~/.apple-tools-mcp/` (`WRITE_SOCKET_NAME`, `writer.sock`). Guard: `tests/unit/write-bridge.test.js`.
- A stale socket file left by a crash is safe: on `EADDRINUSE` the server probes it, a refused connect means nothing is listening, so the file is removed (best effort; if the unlink fails, `listen` fails again) and listening retried; a live daemon makes startup fail. Guard: `tests/unit/write-bridge.test.js` ("takes over a stale socket file left by a crash"). Socket files on some filesystems reject chmod, which is tolerated because the parent directory is 0700. A response that does not parse falls through to the generic "closed without a response" failure.

## `lib/writeGuards.js`

- Every write tool routes its arguments through this module before any AppleScript runs: destructive actions (trash mail, remove event, remove contact) and multi-recipient sends never execute without an explicit `confirm`; `dry_run` always wins and reports what would happen; failures name the action, ids and recipients but never echo bodies. Guard: `tests/unit/write-guards.test.js`.
- `MAX_RECIPIENTS` (25) is a hard ceiling on one send; larger blasts must be split by the caller. `MAX_BODY_LENGTH` (20,000) and `MAX_SUBJECT_LENGTH` (500) keep AppleScript arguments bounded and avoid pathological osascript payloads. The identifier patterns are linear time only (no nested quantifiers) because they run on tool input. A Messages handle is a phone number or an Apple ID email. Mail's `message id` property has no angle brackets, so they are stripped. `validateEventKitId` accepts an EventKit `eventIdentifier`, which may include `/RID=` for recurrences. A mail recipient may be `Display Name <addr@host>` or a bare address.
- `plannedWriteResult`: planned, dry run and confirm blocked results are not deliveries. MCP CallTool only surfaces `message` plus an optional `isError`, and clients that treat a missing `isError` as success would read `ok: true` planned results as delivered, so planned writes return `ok: false` with `planned: true` and `delivered: false`. Guard: `tests/unit/write-guards.test.js` ("returns ok false so MCP isError cannot be read as sent").
- `scrubValues` removes caller supplied content (bodies, subjects) from error text so error paths cannot leak message contents to the client or the logs; the success line names what happened and never includes the body.

## `lib/writeRouting.js`

- macOS attributes Apple events and Contacts or Calendar access to the process responsible for the sender. A stdio MCP server inherits that responsibility from the host app that launched it, so Contacts and Calendar writes can be denied even when node has Full Disk Access. The indexer daemon is launched by launchd, so node is responsible for its own events.
- Policy (`planWriteRoute`): the indexer daemon always executes locally (it is the privileged host); an MCP stdio process delegates to the daemon when the write bridge is up (only for the TCC gated prefixes `contacts_`, `calendar_`, `mail_`, `messages_`); if delegation is impossible it runs locally and, on a TCC denial, explains the host constraint instead of a generic failure. A bridge that is down or broken must not block the write: `planAfterDelegation` falls back to local execution so a single host setup keeps working. The helpers are pure so the policy is testable off macOS.
- Advice differs by host: a Mini LaunchAgent or write bridge host (`detectLaunchAgentContext`: `writer.sock` exists or this process is the daemon) is told to grant the daemon's node Full Disk Access and Automation (`miniLaunchAgentAdvice`, `tccFallbackAdvice`); MacBook, Terminal and the permissions CLI have no `writer.sock` and are told to run from Terminal and Allow the printed `process.execPath` (`terminalAutomationAdvice`) and never to start `apple-tools-indexer`, which is Mini only.

## `lib/writeTools.js`

- Every tool here mutates user data, so each one validates its arguments (no invented recipients, ids or dates), honours `dry_run` (preview, never execute), requires `confirm: true` for deletes and multi-recipient sends, and reports what happened by id, recipient or title, never by echoing bodies. Execution is routed by `lib/writeRouting.js`: the indexer daemon runs writes itself, an MCP stdio process hands privacy gated writes to the daemon.
- `SMOKE_ONLY_AUTOMATION_PROBES` are smoke helpers, never MCP write tools. CallTool uses `isWriteTool`, so these names must stay off `WRITE_TOOL_HANDLERS` or a client could invoke them without `dry_run` or `confirm`. Guard: `tests/unit/write-tools.test.js` (the `SMOKE_ONLY_AUTOMATION_PROBES` assertions).
- `mcpWriteResult` sets `isError` for planned, dry run and confirm blocked results so clients that only check `isError` cannot treat them as delivered; verified sends (`ok: true`) do not set it. Guard: `tests/unit/write-tools.test.js`, "sets MCP isError for planned writes and omits it for verified sends".
- Every send and draft path (stdio, HTTP, the indexer's write bridge) ends in `executeWriteToolLocally`, so the dash rewrite (`withoutDashes`) runs once before claims, Sent checks and Mail or Messages see the text.
- `dispatchWriteTool`: sending tools (`mail_send`, `mail_send_reconcile`, `mail_reply`, `mail_forward`, `messages_send`) fall back to local execution only when the handoff provably did not start a write. A lost response is not evidence of a failed send, so after any handoff that could have reached the daemon the daemon keeps ownership and the result is unconfirmed with no local resend. When the daemon answers but cannot do the write (for example it could not drive Mail's compose window), its reason is the real one because it holds the grants, so a failed local retry returns the daemon's reason. Guard: `tests/unit/write-bridge-logging.test.js` ("logs an unknown outcome without resending after a bridge timeout", "returns the daemon's reason when the local fallback also fails, and logs 'declined'").
- `classifyWriteFailure` gives a one word reason class for logs and never includes addresses, subjects or bodies (write results echo the recipient and subject). `loggedBridgeHandler` wraps the bridge handler so every bridged write leaves one timestamped line (tool, outcome, reason class, duration); the indexer log otherwise has no record of why an overnight send failed. Dry runs and confirm gated previews come back `ok: false` with `planned: true` and are logged as planned, not failed; a send Mail accepted but Sent or Outbox did not show within budget is logged as unconfirmed, not failed. Guards: `tests/unit/write-bridge-logging.test.js`.

## Test suite notes (`tests/`)

Why the tests are the way they are, kept here because the test files carry no comments. Test names say what each test checks; only reasons that are not visible in a name or an assertion live here.

### Fixtures and setup

- `tests/helpers/setup.js` is the Vitest global setup and uses real data sources, no mocking. It sets `APPLE_TOOLS_INDEX_DAYS_BACK` to 30 unless the environment already sets it. It has to run during `setupFiles`, before any test file imports `indexer.js`, because `DAYS_BACK` is a module level constant there; production's default is unlimited and tests keep a 30 day cap so they stay fast. `HOME` must be set for the real data tests.
- `tests/fixtures/stdio-drain-server.js` is a minimal MCP stdio server wired like `index.js` (`bindStdinCloseExit` plus drain on close) with one slow tool, so the drain test needs no Mail access. `DRAIN=0` reproduces the old synchronous exit (guard: `tests/unit/stdio-drain-on-close.test.js`).

### Real data tests

- `tests/indexing/accuracy/real-data-correctness.test.js` and `tests/indexing/caching/real-embedding-cache.test.js` only validate the production index; they never build or rebuild it, so the system index must already exist, and tests that need it skip when it is not indexed. The embedding model is the real `Xenova/all-MiniLM-L6-v2`.
- In `real-embedding-cache.test.js` the "faster on repeated embeddings" check allows the second call up to 20 times the first (and never less than 5 seconds): a model reload is 100 or more times slower, so that still catches a lost cache, while load noise on shared Linux or CI hosts can exceed 3 times and a tight bound would flake.

### Tests with mock embedders and mock tables

- `tests/indexing/accuracy/embedding-consistency.test.js` and `tests/indexing/caching/embedding-cache.test.js` use a deterministic hash based embedder, not a model. Its similarity is not semantic (similar texts may not look similar) and it may not normalize its vectors, so those tests check reproducibility, shape and the concepts (cosine, L2 norm bounds), not real model quality; the real model is checked in the real data tests above.
- `tests/indexing/accuracy/deduplication.test.js`: calendar event ids are built from title and start time, so two events with the same title and start (different calendars) get the same id and collide; in practice the second overwrites or is skipped. The test pins that the collision exists. It is valid for the same title to appear in both email and calendar, because they are different tables.

### Contract, fuzz and chaos tests

- `tests/contract/mcp-protocol.test.js` extracts tool names by reading `index.js` text with a simple pattern (`name: "tool_name"`), not by importing it, and requires at least 80 percent of the expected tools to be found so the check tolerates the pattern missing a few definitions. Defaults and caps asserted there: `validateLimit` defaults to 30 and caps at 1000, `validateDaysBack` defaults to 0 for invalid input and caps at 3650. Response content types include `text` as well as the JSON Schema types.
- `tests/fuzz/properties.test.js`: arbitrary values come from `fc.oneof` of strings, integers, floats, booleans and null, to avoid objects with a problematic `toString`; throwing on edge case input is acceptable. Invariants pinned: escaping adds characters and never removes them; escaping is idempotent only for strings without quotes or backslashes; stripping tags removes characters and leaves no tags; query expansion never returns more than 3 expansions and always includes the original query; a result list is never longer than the requested limit.
- `tests/fuzz/inputs.test.js`: the ReDoS patterns must finish in under 100 ms even for large inputs; for dates, `2024-13-45`, `99/99/9999`, `January 50, 2024`, `Feb 30, 2024` and `2023-02-29` are invalid and `2024-02-29` is a valid leap day; a date may return a timestamp or null, and throwing is also acceptable.
- `tests/chaos/fault-injection.test.js`: LanceDB creates the database when it does not exist, so a missing path opens an empty catalog (no tables). A path that passes validation is fine because file access fails later; paths with a null byte, newline or carriage return, or traversal with a valid extension, must be rejected or sanitized. `tests/concurrency/parallel.test.js` relies on LanceDB handling concurrent opens and queries, so every parallel call must succeed.

### Indexing helpers (`tests/indexing/helpers/`)

- `real-data.js` is "real data only, no rebuilding": the system index at `~/.apple-tools-mcp/vector-index/` is built and maintained by the application (`npm run build-index`), tests assume it exists and only validate it, and they never rebuild it (`buildProductionIndex()` was removed for that reason). It checks which real sources (Mail, Messages, Calendar) exist so tests can skip when data is not available, uses the real `Xenova/all-MiniLM-L6-v2` pipeline (cached across tests, 384 dimensional vectors) and samples real emails with `mdfind` (by content change date) and real messages and events by Cocoa Core Data timestamp (seconds since 2001-01-01).
- `embedderAvailable` is true only on darwin when the Transformers.js `sharp` native loads. This package is darwin only; Linux CI or cloud agent checkouts typically carry a darwin sharp binary and fail with `sharp-linux-x64.node` missing, so the real embedding index tests must skip instead of failing the suite.
- `test-data-generators.js`: the "similar" text pairs carry an expected similarity threshold of 0.7 and the "dissimilar" pairs 0.3; message and event generators take rates (for example 20 percent attachments, 30 percent group chats, 20 percent all-day events, 30 percent recurring); an all-day event lasts 24 hours and a regular one 1 hour; `attributedBodyHex` is only set for messages without text; times are Mac Absolute Time (seconds from the Unix epoch to the Mac epoch is 978307200).
- `performance-utils.js` collects timing, memory and throughput samples; `forceGC` needs `--expose-gc`, and the benchmark helper does a warmup before the measured runs.

### Indexing edge case and integration tests

- Most of these are pure logic tests that restate the indexer's rules on small stand-ins, with no mocking; they pin concepts and edge values rather than call the indexer. Mac Absolute Time is seconds since 2001-01-01 00:00:00 UTC (978307200 seconds after the Unix epoch) and is always UTC; newer macOS stores Messages dates in nanoseconds, detected by a very large value (above 1e15 in the nanosecond test). `tests/indexing/edge-cases/incremental-indexing.test.js` converts Unix milliseconds to Mac Absolute nanoseconds and back like `indexer.js`: year 2000 is negative, a year 3000 value round trips within 1 ms, and an entry exactly at the buffer boundary (last index time minus the 1 hour buffer) is included because the comparison is `>=`, while one 1 ms before is not.
- Ids: calendar ids are `${dbId}-${startTimestamp}`; ids before 1970 are negative timestamps and the hyphen stays valid; the largest SQLite ROWID (9223372036854775807) must validate; message ids often contain email addresses; SQLite may return a number while ids are stored as strings, so the set lookup is type sensitive (a numeric id does not match its string); a set of 100,000 ids (a large mailbox) must stay O(1), with 1,000 lookups in under 10 ms; ids with semicolons or quotes are rejected, as in `validateLanceDBId` and `escapeSQL`.
- `calendar-edge-cases.test.js`: a non-null `recurrence_id` means a recurring event, the occurrence cache holds the real occurrence dates (all with the parent's `owner_id`), timezone conversion happens at display and not in storage (stored start dates are UTC), and a floating event keeps the same local time in every timezone. `message-edge-cases.test.js`: attributed body text is found after an NSString marker followed by a `+` byte (0x2B) and a length byte (lengths above 127 use more than one byte; the test pins only that concept), text must be printable ASCII or extended characters or it is binary garbage, a non-null `attachment_id` from the LEFT JOIN of `message_attachment_join` means an attachment, and `participantCount` 1 is a chat with oneself.
- `email-edge-cases.test.js`: stripping HTML must use the safe pattern (no ReDoS) and finish in under 100 ms on malicious input; header patterns use `[ \t]*` instead of `\s*` so they do not match across newlines; `X-Flagged:Yes` with no space must still count; an invalid date may be NaN or odd but must not throw. `unicode-handling.test.js`: JS `length` counts UTF-16 code units, so an astral character is a surrogate pair and an emoji sequence (family emoji: man, ZWJ, woman, ZWJ, girl) is one grapheme but several code points, spread counts code points, `Intl.Segmenter` (Node 16 or newer) counts graphemes, truncation must not end on half a surrogate pair, and a composed `\u00e9` and `e\u0301` look the same but differ.
- `tests/indexing/integration/background-timer.test.js` uses fake timers: the default index interval is 5 minutes, a cycle starts at once and then every interval, and a tick is skipped while indexing is still in progress (an 8 minute run skips the 5 minute tick and the 10 minute tick runs). `tests/indexing/integration/incremental-indexing.test.js` simulates the `getMessages` filter: Unix milliseconds become Mac Absolute nanoseconds, the effective timestamp is the last index time minus the 1 hour buffer, and already indexed ids are dropped afterward.
- `tests/indexing/contacts/real-contacts.test.js` reads the real AddressBook; tool calls identify a contact by email, phone or name, not by id, and may fail when permissions are not granted. `tests/indexing/edge-cases/real-data-edge-cases.test.js`: an empty search may return everything or throw, and either is acceptable; fewer results than asked is fine when fewer emails exist.

### Indexing integration, negative and performance tests

- These are mostly pure logic tests that restate the indexer's rules on small mocks (a LanceDB table mock, a lock file mock, a file system mock, a timer based progress tracker); they pin the rule and its edge values, they do not call the indexer. The real data files (`tests/indexing/integration/real-data-indexing.test.js`, `tests/indexing/performance/real-data-throughput.test.js`) validate the production index at `~/.apple-tools-mcp/vector-index/`, which must already exist; it is built separately with `npm run build-index` (the error text in several real data tests still says `npm run rebuild-index`, which is not a package script; `build-index` is the real script) and the whole suite skips when no data source or index is present. Real vectors are 384 dimensional and the "similar" and "unrelated" text pairs are separated at a cosine similarity of 0.7.
- `tests/indexing/integration/initial-indexing.test.js`: a first run is a catalog with no tables, so the indexer takes the full scan (`find`) path, creates each table with `mode: overwrite`, and then writes the index metadata. `reindex-workflow.test.js`: `rebuild_index` clears only the requested sources (all of them when none are named), runs with a forced full scan so the last index time is treated as null, takes the indexer lock so a second rebuild fails, and returns at once while the rebuild runs in the background.
- `tests/indexing/integration/lock-file.test.js`: a lock whose PID no longer exists (ESRCH) is stale and is removed; a lock held by another live process refuses the second taker; the lock file is created with the `wx` flag so creation is exclusive, fails with EEXIST when the file exists and prevents a time of check to time of use race; the lock is released on process signals and when stdin closes (client disconnect); if the lock cannot be written the indexer fails safe and does not proceed without it. The age limit is 30 minutes (`LOCK_TIMEOUT_MS`, 1,800,000): a lock exactly 30 minutes old is not stale (the test uses `>`, not `>=`), 35 or 45 minutes is stale, an old format lock with no timestamp defaults to now, and a lock older than the limit is removed even if its process still exists (PID check with signal 0).
- `tests/indexing/integration/progress-monitoring.test.js` (fake timers): the progress check runs every minute (`PROGRESS_CHECK_INTERVAL_MS`) and the process counts as hung after 10 minutes with no progress (`MAX_NO_PROGRESS_MS`); progress every 2 or 5 minutes keeps it healthy over 30 minutes and 2 hours, 9 minutes of silence is fine, and exactly 10 minutes reaches the limit.
- `tests/indexing/negative/`: failures must be handled gracefully and partial progress must be kept. `database-failures`: the test uses its own batch size of 32 (production `indexer.js` uses 64), a failure at batch 2 leaves 64 processed (batches 0 and 1) and 36 of 100 remaining to resume, and a query slower than its timeout is cut off. `embedding-failures`: a zero vector is normalized to a uniform vector (`1/sqrt(n)`) instead of dividing by zero, NaN and Infinity never reach a stored vector, successful items are saved immediately, token counts use a rough 4 characters per token, and with failures on indexes 8 to 23 of each batch of 32, 16 fail and 16 succeed per batch (32 of 64 overall). `lancedb-failures`: a failed batch is logged and the next batch continues (batch delete pattern from `indexer.js`), items with the wrong dimension (100 instead of 384) or NaN values are rejected while the rest are added, a dropped connection fails once and succeeds on reconnect, and a deleted table fails to reopen gracefully.
- `metadata-corruption`: an unparseable metadata file (malformed JSON, single quotes) yields an empty object; a timestamp must be a finite non-negative number and not more than 1 day in the future (a week ahead is rejected, 30 days back is fine); `JSON.stringify(NaN)` becomes `null`, so NaN is tested through an invalid type; two unlocked concurrent updates can lose one (counter 1 instead of 2) and the test documents that race, while the locked version applies both; the schema migrates v1 to v2 by renaming `indexTime` to `lastIndexTime`, and v2 to v3 by splitting `lastIndexTime` into the message, email and calendar timestamps, then sets version 3.
- `timeout-handling`: the `withTimeout` helper mirrors `indexer.js` and `index.js` and clears its timer whether the promise fulfills or rejects (the timer is also unref'd); production budgets are 30 seconds for a batch embedding and 10 seconds for a single embedding, and the tests use 100 ms budgets (and 500 ms test timeouts) instead; a hanging batch falls back to embedding items one at a time, and an item that times out gets a zero vector fallback while the others keep their embeddings.
- `tests/indexing/performance/`: these tests define their own `BATCH_SIZE` of 32 and, in `batch-efficiency.test.js`, a `BATCH_DELAY_MS` of 100; production `indexer.js` uses 64 and 0 (see the `BATCH_SIZE` note above), so the tests check the batching arithmetic, not the production values. In the test model the delay is applied between batches and not after the last one, 100 items make batches of 32, 32, 32 and 4, and a batch can be garbage collected before the next so no more than `BATCH_SIZE` items are held. Tolerances are loose on purpose because pure logic timing is noisy: time per item within 3 times the average, throughput at the largest size not below 50 percent of the smallest, the coefficient of variation of batch durations under 3 (300 percent), and for real embeddings under 2 seconds each, 30 seconds for a batch, under 5 seconds per search, and a warm query under twice the cold query or under 50 ms. The test "consistent throughput over multiple batches" is skipped because it times `Promise.resolve()`, which is sub-microsecond and dominated by measurement noise (it keeps a warmup batch to avoid V8 JIT cold start and asks for a minimum of at least 30 percent of the average).

### Indexing resource, security and unit tests

- Most files here are pure logic tests that need no mocking; they restate a rule with a small local model (a lock mock, a simulated sanitizer) and pin its edge values. Several files open with a "Standard indexer constants" label for `BATCH_SIZE` 32 (and `BATCH_DELAY_MS` 100, `EMBEDDING_DIM` 384). That label was wrong for the batch values: these are the tests' own constants, and production `indexer.js` uses `BATCH_SIZE` 64 and `BATCH_DELAY_MS` 0 (see the `BATCH_SIZE` note above). The 384 dimension is the real one for all-MiniLM-L6-v2, and `tests/indexing/unit/batch-embedding.test.js` pins it. Real data and real embedding suites skip unless `embedderAvailable()` is true; `tests/indexing/unit/embedder-available.test.js` guards this by reading six real-data suites (caching, accuracy, integration, edge-cases, performance, resource) and requiring `skipIf(!sources.embedder)` in each, because the Transformers.js sharp native is darwin only and the package is darwin only, so these suites must skip on Linux.
- `tests/indexing/resource/concurrent-access.test.js`: its `createLockFileMock` lets the holder re-acquire (the same PID succeeds) and refuses a different PID; only the holder can release, so PID 2 cannot release PID 1's lock. The stale lock test hard codes `isStale = true` where real code would check `!processExists(stalePid)` (the real PID check is tested in `tests/indexing/integration/lock-file.test.js`), and the age test uses a 1 second limit with a 100 ms wait so the lock never times out (the real limit is 30 minutes). Exclusive creation is modeled after the `wx` flag: the first create succeeds and the second fails, and of several near simultaneous attempts exactly one wins. The SIGTERM and SIGINT tests only call a registered handler by hand and check the lock is released. The re-entrant test counts depth: the lock is released only when the depth returns to 0. A write takes a single writer slot and a second writer is refused with `writer busy` while one is writing, so at least one of several concurrent writers succeeds.
- `tests/indexing/resource/cpu-throttling.test.js`: the delay is applied between batches and never before the first, so N batches wait `(N - 1) * BATCH_DELAY_MS` in total (64 items are 2 batches, 96 are 3, 128 are 4); a single batch has no delay; measured gaps may be 10 percent under the delay (`BATCH_DELAY_MS * 0.9`) because timers are inexact; a throttled run is slower than an unthrottled one by about the delay time; other work can interleave during a delay (a 50 ms wait). The "adaptive delay" test is only a concept demonstration with a fixed base delay, no adaptive logic exists.
- `tests/indexing/resource/memory-leak.test.js` and `memory-usage.test.js`: loose bounds because heap size is noisy. Leak tests force garbage collection when the runtime exposes it (`--expose-gc`), then require: the largest later cycle under 1.5 times the average of later cycles plus 10 MB (the first cycle is warmup), closures and listeners and a reusable buffer do not accumulate, duplicate subjects are not retained, final memory under 2 times the 25 percent sample plus 20 MB, and a simulated weak cache holds at most 5 entries. Usage tests: peak heap under 300 MB (sampled every 5 batches, for emails, messages and calendar events), under 50 MB growth over 640 items (20 batches), one batch in flight at a time, 10 KB bodies growing under 200 MB, and vector storage of 384 floats at 4 bytes (1,536 bytes) each is under 2 MB for 1,000 vectors (about 1.46 MB).
- `tests/indexing/resource/real-data-resources.test.js`: needs the real embedder. 20 embeddings grow the heap under 500 MB; repeated batches stay under 200 MB total (the model stays loaded, with room for buffers); searches grow it under 100 MB, run for at most 10 seconds or 50 queries, whichever comes first; an indexed item uses under 10,000 bytes including the vector; CPU time is converted from microseconds to milliseconds. The event loop yield test is skipped (`it.skip`) because it is timing and hardware dependent: it fails where 5 embeddings take over 500 ms.
- `tests/indexing/security/applescript-injection.test.js` uses local simulations of the sanitizers, not the library functions: backslashes are escaped first and then quotes (so an added backslash is not doubled again), and carriage returns and newlines become `\r` and `\n`, which stops a quote or a newline breaking out of the string; the shell wrapper escapes a single quote as `'\''` (close the quote, an escaped quote, reopen). Message IDs use an allow list of letters, digits and `@.<>-_+=` up to 500 characters (RFC 2822 msg-id is printable ASCII); contact identifiers drop everything but letters, digits and `@.-_+` and spaces; `message://` URLs allow only letters, digits and `-_.~%@<>` in the path; calendar IDs allow letters, digits, dashes and underscores; backslashes in paths become forward slashes first, then quotes and colons (the AppleScript path separator) are escaped; targets with newlines or control characters are rejected. The file also imports the real exports from `lib/mailWrite.js` (`ATM_FOCUSED_WHOSE_QUERY`, `ATM_FOCUSED_AX_QUERY`, `ATM_APPLESCRIPT_RESERVED_SHORTS`).
- `tests/indexing/security/config-path.test.js`: the config file must stay under `~/.apple-tools-mcp/`; its contents are data, not instructions or alternate filesystem roots, so a `configPath` key inside the file is ignored instead of followed.
- `tests/indexing/security/path-traversal.test.js` models `validateEmailPath` (the library one is `validateEmailPath(filePath, mailDir)` in `lib/validators.js`): the path must be a non empty absolute string, must not contain `..`, must be under `~/Library/Mail` and must end in `.emlx` or `.partial.emlx`. Traversal is rejected before normalizing, because after `path.normalize` `/Library/Mail/../../../etc/passwd` becomes `/etc/passwd` and escapes; URL encoded forms (`%2e%2e%2f`, and double encoded `%252e%252e%252f`, whose second decode shows `../`) are decoded and rechecked, malformed encodings are rejected, a symlink that resolves outside the Mail directory must be rejected after a real path check, trailing slashes are stripped by hand because `path.normalize` keeps them, a path component may have no separators, no `.` or `..` and no null byte, and because macOS is case insensitive `/Library` and `/library` must compare equal after lowercasing.
- `tests/indexing/security/sql-injection.test.js`: `escapeSQL` doubles single quotes, so `'; DROP TABLE users; --` becomes a valid string literal in `WHERE x = '...'` instead of an injection (curly quotes `‘` and `’` are separate characters from the ASCII quote); the library version in `lib/validators.js` also doubles backslashes. `validateLanceDBId` accepts letters, digits, hyphen, underscore and dot (a double hyphen is fine because it is only data in a quoted literal); calendar IDs look like `title-timestamp` and may be more permissive but never contain a quote, semicolon, backslash or double quote; the parameterized form keeps its placeholder unreplaced while the concatenated form is vulnerable; LIKE patterns escape `%` and `_` (the wildcards) as well as quotes; SQLite identifiers are letters, digits and underscore and may not start with a digit.
- `tests/indexing/unit/batch-delete.test.js`: stale IDs are validated and SQL escaped first, invalid ones are counted as skipped, then deleted in chunks of 100 as an `id = '...' OR ...` condition (`BATCH_DELETE_SIZE` 100 in `indexer.js`); a failed chunk is counted and does not stop later chunks (150 deleted of 3 chunks when chunk 2 fails). The test's own `validateLanceDBId` (letters, digits and `._@<>:-/` and whitespace, up to 1,000 characters) and `escapeSQL` are not the production ones: production `lib/validators.js` allows letters, digits, whitespace and `-:,.` and caps IDs at 500 characters, and its `escapeSQL` doubles backslashes too. Query sizes are checked as sanity bounds: 100 conditions of about 45 characters stay under 10,000 characters, and 100 IDs of 1,000 characters (about 100,700 characters) stay under 110,000.
- `tests/indexing/unit/batch-embedding.test.js` is conceptual: empty input returns empty output, one text needs no batching, every text gets `EMBEDDING_DIM` values, a normalized vector has magnitude near 1 with values in -1 to 1, the same input gives the same output (a hash stands in for determinism), the pipeline is created on first use and the same instance is reused, identical vectors have cosine similarity 1 and orthogonal ones 0, similar synthetic vectors score above 0.9, 512 is the common token limit, and empty text is handled without error.

- `tests/indexing/unit/orchestration.test.js` (pure logic, a lock mock): it models `index.js`. - `tests/integration/calendar-date-live.test.js`: `calendar_date` reads one row per occurrence from `OccurrenceCache` (the `oc.day` range), works on a copy of Calendar.sqlitedb in `/tmp` and leaves no copies behind, and uses local time bounds with no hard coded time zone (`'localtime'`, never `America/Chicago` or `America/New_York`); the Apple (Mac absolute) bounds are the local day start and end in seconds minus `MAC_ABSOLUTE_EPOCH`. - `tests/integration/periodic-indexing-e2e.test.js`: an end to end test of the periodic email pass, run on a temp directory only. A new email lands in a fake Mail folder after a first pass, the next `indexEmails()` pass (what every indexer cycle runs first) must index it, and `searchEmails()` (the `mail_search` path) must find it by its unique marker and by meaning, using the real embedding model and real LanceDB. Isolation, so it is safe next to the live indexer on the Mini: `HOME`, `APPLE_TOOLS_INDEX_DIR` and `APPLE_TOOLS_META_FILE` point into the temp dir (like `tests/unit/indexer-email-pass.test.js`), so the live `~/.apple-tools-mcp` index and `~/Library/Mail` are never read or written; there is no Mail.app, no AppleScript and no email sent, the "new email" is a synthetic `.emlx` file; a guard asserts `indexer.INDEX_DIR` is the temp index before indexing. It is opt in with `RUN_E2E_TESTS=1` (`RUN_E2E_TESTS=1 npx vitest run tests/integration/periodic-indexing-e2e.test.js`); its 5 minute timeout allows for the first run downloading the embedding model.
- `tests/integration/real-data.test.js` runs against the real LanceDB index and Apple databases and skips when the index does not exist (it reports the skip reason). Vectors have 384 dimensions (MiniLM-L6-v2) and the same dimension for all rows, distances run from 0 (perfect) to 2 (opposite) and results come back sorted by distance ascending, mail paths are under the Mail directory, and phone or email format is accepted for message handles. The date test is skipped (`it.skip`): the production index is unlimited by default, so dates are not limited to a 30 day window; it is kept as a sanity check that dates parse and are not in the far future (one day of future allowed for time zones).
- `tests/integration/tools.test.js`: pure logic checks of the tool schemas, response format, input validation, error handling and cross-tool workflows (results carry the fields that enable follow up queries), smart search intent detection (calendar, messages and email signals, default is to search all sources), and an embedding cache model with a 5 minute TTL (`CACHE_TTL`), at most 100 entries (`CACHE_MAX`) and eviction of the oldest entry when full.
- `tests/perf/background-indexing.perf.test.js`: models of system impact while indexing, all simulated: CPU time is `process.cpuUsage()` in microseconds divided by 1000 for ms, the event loop must not be blocked for long, searches run concurrently with indexing, indexing pauses for priority user requests, incremental passes only look at items from the last minute (60,000 ms), overhead assumes 0.01 ms per progress update, an interrupted run resumes, concurrent indexing of the sources should be faster than sequential, and memory must not grow unboundedly (forced gc when exposed).
- `tests/perf/datasources.perf.test.js`: parsing and formatting speed models, with 5,000 simulated `mdfind` paths, a simplified NSAttributedString extraction, free time slots modeled as gaps over 30 minutes between consecutive events, of which only slots of at least 1 hour are kept (the old `workStart` 9 AM and `workEnd` 5 PM constants were never read, so they were removed; the model does not limit slots to working hours), and 52 weekly occurrences for a year.
- `tests/perf/date-parsing.perf.test.js`: `chrono-node` is replaced by a mock with realistic timing; ambiguous inputs (`1/2/2024` is Jan 2 or Feb 1, `03-04-2024` is March 4 or April 3, `next week Monday`) must parse without error whichever reading is chosen; Mac absolute time counts from January 1 2001 (the test uses 0, -1, the 32 bit maximum 2147483647 and the current time in Mac seconds, plus random Mac timestamps). The date formatting test runs five formats with 500 iterations each; the benchmark helper sleeps 10 ms between iterations, so about 25 seconds are deliberate cooldown and the test timeout is 60 seconds, while the assertion stays on the measured mean of under 2 ms.
- `tests/perf/edge-cases.perf.test.js`: boundary inputs must be fast and not throw: empty arrays and empty content are skipped, non breaking and em space strings, dates at the Unix epoch, the Mac epoch (978307200000 ms, 2001), the 32 bit overflow in 2038 and just before the Unix epoch, future dates, US daylight saving transitions in 2024 (March 10 spring forward and November 3 fall back, plus the minutes just before and after), time zones at the extremes (`Pacific/Kiritimati` UTC+14, `Pacific/Midway` UTC-11, unsupported zones), leap days (2024, 2000 and the 2100 non leap century rule), common words in every document, stop words, negation, regex special characters escaped, mail thread trees with roots and orphans whose parents do not exist, contact lookup by each email, multi day events expanded to day occurrences, 52 weeks of recurrences, overlapping and duplicate events, and records with random fields removed.
- `tests/perf/embedding.perf.test.js` benchmarks either the real model `Xenova/all-MiniLM-L6-v2` or a fast mock. `USE_REAL_DATA` set to `1` or `true` together with available real data (`isRealDataAvailable()`) selects the real model, which is loaded once in `beforeAll` (the log says `USING REAL EMBEDDING MODEL`); otherwise the suites run against `createFastEmbedder()` from `tests/perf/helpers/mocks.js` (the log says `USING MOCK EMBEDDINGS`), and only the "Single Text Embedding" suite skips (`describe.skipIf(!useRealData)`). An older header said all mock support was removed and the tests skip without real embeddings; that was not true. Real model bounds: pipeline access when cached under 50 ms, one embedding under 100 ms, a batch of 32 under 2,000 ms, 100 texts in batches of 32 under 10,000 ms, a cache hit under 5 ms, latency histogram mean under 200 ms, and for the length test 500 words may be up to 10 times slower than 10 words, a 50 times longer text (7.7 times was measured on this hardware). Mock bounds are tighter: pipeline access under 50 ms and cached access under 10 ms, a batch of 32 under 100 ms, 100 texts under 500 ms, a cache hit under 5 ms, histogram mean under 10 ms. Both: throughput at batch size 64 must be at least 0.3 of the batch size 8 throughput, a cache hit pass is faster than the all-miss first pass, heap growth stays under 200 MB for the 20 batch run and under 100 MB for the leak run (real runs use more memory than the mock), and for vector operations a cosine similarity averages under 1 ms, a top k search under 500 ms and vector normalization under 10 ms.
- `tests/perf/helpers/benchmark.js`: `measureTime` is a high precision timer for async and sync functions, `getMemoryUsage` returns MB, `benchmark` runs a warmup (default 3 iterations, collecting gc if asked), then the measured iterations with a `cooldownMs` sleep between them (default 10 ms), and reports latency percentiles, throughput in items per second, a console reporter, a latency histogram, a comparison against the first benchmark as baseline, a `wait` helper and a forced gc when `global.gc` exists.
